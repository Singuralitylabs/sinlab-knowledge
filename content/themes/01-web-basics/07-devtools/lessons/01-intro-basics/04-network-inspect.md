# Network：リクエストの絞り込みとレスポンス確認

## 解説

ページを読み込むと、HTML本体・CSS・JavaScript・画像・API通信など、多数のリクエストがNetworkパネルに記録されます。目的の通信を素早く見つけるには、フィルターと検索を組み合わせます。

### フィルタータブでの絞り込み

| フィルター | 表示される通信 |
|------------|----------------|
| `All` | すべての通信 |
| `Fetch/XHR` | 非同期通信（API呼び出し）のみ |
| `Doc` | HTMLドキュメント本体 |
| `CSS` / `JS` / `Img` | 各リソース種別ごと |

APIのデバッグ中は`Fetch/XHR`だけに絞ると、画像やCSSのノイズが消えて目的のリクエストを見つけやすくなります。フィルタータブの左にあるFilter欄にURLの一部を入力すれば、さらに絞り込めます。

### リクエスト詳細の確認

一覧の中から通信行をクリックすると、右側に詳細パネルが開きます。

| タブ | 確認できる内容 |
|------|----------------|
| `Headers` | リクエストヘッダー、レスポンスヘッダー、ステータスコード（`200` `404` `500`等） |
| `Payload` | リクエスト時に送信したパラメータやJSONデータ |
| `Response` | サーバーから返された生データ |
| `Preview` | JSONを折りたたみ表示など、整形された見やすい形式 |

---

## ありがちなつまずき

### 1. リクエストが一覧に出てこない

```text
❌ ページ読み込み後にNetworkパネルを開いても、
   すでに終わった通信が記録されていないと勘違いする

✅ Networkパネルを開いた状態でページをリロード（Ctrl/Cmd + R）する。
   パネルを開く前の通信は記録されていないことが多い
```

### 2. ステータスコードだけ見て中身を確認しない

`200 OK`が返っていても、レスポンスの中身（`Response`/`Preview`タブ）が期待した形式になっていないことがあります。ステータスコードは「通信自体は成功した」ことしか示さないため、データの中身は必ず別途確認します。

---

## 実用例

### APIが期待通りのデータを返しているか確認する

フロントエンドで表示が崩れたとき、まずNetworkパネルで該当のAPIリクエストを`Fetch/XHR`フィルターで探し、`Preview`タブでレスポンスの構造を確認します。バックエンド側の問題か、フロントエンド側の描画処理の問題かを素早く切り分けられます。

### 送信しているリクエストパラメータを確認する

フォーム送信や検索機能が期待通りに動かないとき、`Payload`タブで実際に送信されているパラメータを確認すれば、フロントエンドのコードを読まなくても送信内容の誤りに気づけます。
