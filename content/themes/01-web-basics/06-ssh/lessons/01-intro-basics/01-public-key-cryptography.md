# 公開鍵暗号方式による認証の仕組み

## 解説

SSH認証は、**公開鍵暗号方式**という技術を使って「パスワードを送らずに本人確認をする」仕組みです。ペアになった2つの鍵、**公開鍵（Public Key）**と**秘密鍵（Private Key）**を使います。

```text
[ 自分のPC (Client) ]                       [ GitHub / Remote Server ]
  ├── 秘密鍵 (id_ed25519)  ──(非公開)
  └── 公開鍵 (id_ed25519.pub) ───────────────>  ~/.ssh/authorized_keys
                                                    (またはGitHubアカウントのSSH Key)
```

| 鍵の種類 | 保管場所 | 役割 |
| :--- | :--- | :--- |
| 公開鍵 (Public Key) | サーバー側（GitHub等）に登録 | 「この人の秘密鍵に対応する相手だ」と検証するための鍵。公開しても安全 |
| 秘密鍵 (Private Key) | 自分のPCにのみ保管 | 本人であることを証明する鍵。**絶対に他人に渡してはいけない** |

### 認証の流れ（チャレンジ・レスポンス方式）

1. **接続要求**：クライアントがサーバーへ接続をリクエストします
2. **チャレンジ**：サーバーはランダムなデータ（チャレンジ）を、登録済みの公開鍵で暗号化してクライアントに送ります
3. **レスポンス**：クライアントは自分の秘密鍵でそれを復号し、その応答（署名）をサーバーに返します
4. **検証・承認**：サーバーは送られてきた応答を検証し、正しければログインを許可します

```text
Client                                   Server
  |  1. 接続要求                             |
  | ---------------------------------------> |
  |  2. チャレンジ（公開鍵で暗号化したデータ）    |
  | <--------------------------------------- |
  |  3. レスポンス（秘密鍵で復号して署名）       |
  | ---------------------------------------> |
  |  4. 検証OK → ログイン許可                  |
  | <--------------------------------------- |
```

**重要なポイント**：この一連のやり取りの中で、秘密鍵そのものはネットワーク上を一切流れません。パスワード認証のように「秘密の情報を相手に送信する」必要がないため、通信を盗聴されても秘密鍵が漏れる心配がないのです。

## コマンドサンプル

鍵ペア自体の生成コマンドは次の記事（`ssh-keygen`）で扱いますが、ここでは仕組みを確認するための基本コマンドを紹介します。

```bash
# 現在自分のPCにある鍵の一覧を確認する
ls -la ~/.ssh

# 公開鍵の中身を表示する（サーバーに登録するのはこちら）
cat ~/.ssh/id_ed25519.pub

# 秘密鍵のファイル権限を確認する（600 であるべき）
ls -l ~/.ssh/id_ed25519
```

## 実行結果

```text
$ ls -la ~/.ssh
drwx------  5 taro  staff   160  1 15 10:00 .
drwxr-xr-x  20 taro staff   640  1 15 09:50 ..
-rw-------  1 taro  staff   411  1 15 10:00 id_ed25519
-rw-r--r--  1 taro  staff    98  1 15 10:00 id_ed25519.pub
-rw-r--r--  1 taro  staff  1704  1 15 10:05 known_hosts

$ cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIP1k... your_email@example.com

$ ls -l ~/.ssh/id_ed25519
-rw-------  1 taro  staff  411  1 15 10:00 id_ed25519
```

`id_ed25519` の権限が `-rw-------`（`600`）になっている点に注目してください。所有者以外は読み書きできない状態で保護されています。

## よくある間違い

### 1. 秘密鍵と公開鍵を混同する

```text
❌ 秘密鍵（拡張子なしのファイル）をサーバーやチームメンバーに送ってしまう
   → 秘密鍵が漏れると、本人になりすましてログインできてしまう

✅ サーバーやサービスに登録するのは必ず「.pub」が付いたファイル（公開鍵）
```

### 2. 秘密鍵の権限が緩いまま使ってしまう

```bash
# ❌ 権限が緩いと SSH 側が「安全でない」と判断して接続を拒否することがある
$ chmod 644 ~/.ssh/id_ed25519

# ✅ 秘密鍵は所有者のみ読み書き可能にする
$ chmod 600 ~/.ssh/id_ed25519
```

### 3. 「暗号化通信＝SSH認証」だと思ってしまう

```text
❌ 「SSHは通信を暗号化するだけの技術」という理解で止まってしまう

✅ SSHは「通信の暗号化」に加えて「公開鍵暗号方式による本人確認（認証）」も行う
   → HTTPS通信の暗号化とは別に、"誰がアクセスしているか" を保証する仕組みがある
```

## 実用例

### 秘密鍵の安全な扱い方をチームで共有する

```text
【やってよいこと】
・秘密鍵は自分のPC内（~/.ssh 配下）にのみ保管する
・パスフレーズを設定して、鍵ファイル自体が漏れても悪用されにくくする
・PCを廃棄・譲渡する前に秘密鍵を確実に削除する

【やってはいけないこと】
・秘密鍵をSlackやメールで送る
・秘密鍵をGitリポジトリにコミットする（.gitignore で除外する）
・複数人で同じ秘密鍵を使い回す（鍵は1人1ペアが原則）
```

### 鍵が漏洩した疑いがある場合の対応

```bash
# 1. 新しい鍵ペアを生成する
ssh-keygen -t ed25519 -C "your_email@example.com"

# 2. サーバー側（GitHub等）から古い公開鍵を削除する

# 3. 新しい公開鍵を登録し直す
cat ~/.ssh/id_ed25519.pub
```

## 実習

### 課題1：鍵ファイルの権限を確認する

1. `ls -la ~/.ssh` を実行し、自分のPCにどんな鍵ファイルがあるか確認してください
2. 秘密鍵（拡張子なしのファイル）の権限が `600`（`-rw-------`）になっているか確認してください
3. もし権限が緩い場合は `chmod 600 <秘密鍵のパス>` で修正してください

### 課題2：公開鍵と秘密鍵を見分ける

1. `~/.ssh` の中にあるファイルを1つずつ見て、どれが公開鍵でどれが秘密鍵か判断してください
2. 判断の根拠（ファイル名の末尾、ファイルの中身の書き出し文字列など）を言葉で説明してみてください

### 課題3：チャレンジ・レスポンス方式を図解する

1. 本文中の図を見ずに、自分の言葉で「クライアント → サーバー → クライアント」のやり取りを説明してみてください
2. なぜ秘密鍵を送らなくても本人確認ができるのか、その理由を1〜2文でまとめてください
