# なぜGAS開発には別のアプローチが必要なのか

一般的な Web 開発やバックエンド開発では、Cursor や Claude Code などの AI コーディングエージェントが目覚ましい成果を上げています。ローカルのファイルを読み込み、ターミナルでテストを実行し、エラーが出たら自動で自己修正する——これが現代の AI 駆動開発の標準形です。

しかし、**Google Apps Script（GAS）の開発現場では、この恩恵をそのまま受けることが困難でした**。GAS は「ブラウザ完結」であることが最大の長所であったがゆえに、エージェント型の生成 AI ツールとは決定的に噛み合わない構造を抱えているためです。

本ページでは、なぜブラウザ完結の GAS が AI 開発と衝突するのかを解剖し、それを乗り越えるための **4 つのアプローチ** を比較します。

## このページで学べること

- ブラウザ完結型 GAS 開発が抱える 3 つの構造的課題
- AI ツールとの「相性の悪さ」の根本原因
- GAS 開発で AI を使う **4 つのアプローチ** の比較表
- なぜローカル降下（clasp × Claude Code）が中・大規模開発で最強の選択肢になるのか

## ブラウザ完結型 GAS が AI と噛み合わない 3 つの理由

GAS のオンラインエディタは、環境構築なしですぐに動かせる素晴らしい環境です。しかし、生成 AI を本格的に組み込もうとすると、次の 3 つの壁に直面します。

```text
[従来の GAS 開発環境]               [AI コーディングエージェント（Claude Code 等）]
  ブラウザ内のエディタ                 ローカルのファイルシステム
  コードは Google のクラウド上 ──(断絶)──>  コードを直接読み書きできない
  バージョン履歴は簡易的                   Git で差分を追跡・ブランチ管理
  実行・ログはブラウザ内のみ                ターミナルでテスト・コマンドを自動実行
```

### 1. コードがローカルに存在しない（ファイルアクセスの断絶）

Claude Code や Cursor などのコーディングエージェントは、ローカルのファイルシステム上にあるコードを読み取り、ディレクトリ構造や設定ファイルをコンテキスト（文脈）として把握します。

しかし、ブラウザ上で書いているスクリプトは Google のクラウド上にのみ存在するため、ローカルの AI ツールからはコードが見えません。

### 2. Git によるバージョン管理がない

ブラウザエディタにも「履歴」機能はありますが、コミットメッセージを付けて差分を管理したり、トピックごとにブランチを切って pull request でレビューしたりすることはできません。

AI に大胆なリファクタリングを指示しても、「壊れたら直前のコミットに `git reset` する」という安全弁がないため、手作業で Ctrl+Z を押すような恐る恐るの開発を強いられます。

### 3. 検証ループがブラウザ内でしか回らない

AI 駆動開発の真骨頂は、[ループエンジニアリング](/themes/04-ai-driven-development/01-overview/loop-engineering) で解説されている「AI がコードを書き、テストを実行し、失敗したら自分で直す」という自律ループです。

しかし、GAS の実行ボタンはブラウザの画面上にあり、エラーログもブラウザのコンソールに流れます。人間が画面を見てエラーをコピーし、AI チャットに貼り付ける「人間バケツリレー」が発生し、エージェントの自律性が完全に奪われてしまいます。

## AI を活用する 4 つのアプローチ比較

GAS 開発において生成 AI を活用する方法は、大きく分けて以下の 4 つが存在します。

| アプローチ | 概要 | 開発環境 | Git 管理 | 検証の自動化 | 最適なユースケース |
| --- | --- | --- | --- | --- | --- |
| **① チャットコピペ** | ChatGPT / Claude 等の Web チャットにコードを貼り付けて相談 | ブラウザ | なし（手動） | 不可（人間が転記） | 数行〜数十行の単発スクリプト、初歩の質問 |
| **② Gemini サイドパネル** | Apps Script エディタ右側に統合された Gemini に直接指示 | ブラウザ | なし | エディタ内完結（半自動） | 1 ファイル・数十行程度の小規模修正、ブラウザで即座に完結させたい場合 |
| **③ clasp + コーディングエージェント** | clasp でコードをローカル同期し、Claude Code / Cursor で編集 | ローカル | **あり（完全）** | CLI コマンドによる半自動〜自動検証 | 複数ファイル、中〜大規模な業務アプリ、チーム開発 |
| **④ clasp mcp + エージェント** | clasp 3.x の MCP サーバー（プロジェクト同期）と CLI を統合 | ローカル | **あり（完全）** | **可能（AI が直接 push/同期、CLI でテスト）** | **本格的な AI 駆動開発、テスト・検証ループの自律化** |

### ① チャットコピペ（原始的アプローチ）

ブラウザのチャット画面に「スプレッドシートの A 列を読んでメールを送るコードを書いて」と頼み、出力されたコードを手作業でエディタに貼り付ける方法です。

環境構築が不要な反面、プロジェクト全体の見通しが AI に伝わらず、ファイルの往復コピペに追われることになります。

### ② Gemini サイドパネル（ブラウザ完結型の選択肢）

2026 年 8 月よりロールアウトされた、Apps Script エディタ公式の AI 支援機能です。エディタの右側に Gemini が常駐し、開いているコードの修正やエラーの自動解説、関数の生成を行ってくれます。

「環境構築を一切したくない」「数行の簡単な関数を今すぐ直したい」という場合には最も手軽な選択肢です（※有償の Google Workspace ライセンスまたは Google AI サブスクリプションが必要です）。

しかし、複数ファイルにまたがる設計や、Git による履歴管理、ローカルの自動テストツールとの連携はできません。

### ③ clasp + コーディングエージェント（ローカル降下）

Google 公式の CLI ツール `clasp`（Command Line Apps Script Projects）を使い、GAS のプロジェクトをローカルのファイル（`.js` や `.json`）としてダウンロードします。

コードがローカルに降りてくることで、VS Code や Git、TypeScript、npm パッケージが利用可能になり、Claude Code や Cursor がローカルのプロジェクト全体を自由に探索・編集できるようになります。

### ④ clasp mcp + エージェント（次世代の自律エージェント連携）

clasp 3.x で実験的に導入されたのが、AI エージェントとツールをつなぐ標準プロトコル **MCP（Model Context Protocol）** のサポートです。

Claude Code に clasp mcp を組み込むことで、AI はローカルファイルの編集だけでなく、プロジェクトのファイル同期ツール（`push_files` / `pull_files`）を自律的に呼び出せるようになります。さらに CLI のテストコマンド（`clasp run-function`）を組み合わせることで、「コードを更新 → クラウドに push → リモートテスト実行 → ログを確認して自己修正」という一連の検証ループをエージェントに任せられるようになります。

## 本テーマが目指すゴール

本テーマ「Google Apps Script」では、初心者向けにブラウザでの基本（モジュール 1）とスプレッドシート操作（モジュール 2）を押さえた上で、**「③ clasp」および「④ clasp mcp × Claude Code」を中心とした開発手法** をマスターすることをゴールとします。

一度ローカルに環境を落とし、Git と Claude Code を組み合わせるワークフローを確立すれば、GAS 開発の生産性と信頼性は劇的に向上します。

## まとめ

- **ブラウザ完結の限界**: ファイルのローカル不在・Git 不在・検証のブラウザ閉じ込めにより、エージェント型 AI との相性が悪い。
- **4 つのアプローチ**:
  - コピペ（手軽だが限界が早い）
  - Gemini サイドパネル（ブラウザ内での手軽な小修正に最適）
  - clasp + AI エージェント（ローカル環境と Git を手に入れる標準形）
  - clasp mcp + エージェント（ファイル同期ツールと CLI を組み合わせて自律開発を加速する最先端の形）
- **結論**: 本格的な業務アプリケーションを AI とともに高速かつ安全に開発するには、clasp によるローカル環境構築が不可欠である。
