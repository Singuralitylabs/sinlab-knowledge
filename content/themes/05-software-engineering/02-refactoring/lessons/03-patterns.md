# 定番のリファクタリングパターン

リファクタリングには定石となる「型」があります。どんなコードでも、結局は **重複の排除・命名の改善・関数の抽出・条件分岐の整理** といった少数のパターンの組み合わせで改善できます。本ページでは、これらの代表的なパターンを解説します。

## このページで学べること

- 代表的な **リファクタリングパターン** 4 つ
- 各パターンの **適用方法と注意点**
- 過度な適用（やりすぎ）を避ける考え方

## 1. 重複の排除（DRY）

同じロジックが複数箇所にコピーされている状態を、1 つの関数にまとめます。**DRY（Don't Repeat Yourself）** と呼ばれる原則です。

重複があると、1 箇所を直したときに他の箇所も直す必要があり、直し忘れがバグになります。共通化すれば修正は 1 箇所で済みます。

> [!CAUTION]
> 「形が同じ ＝ まとめるべき」ではありません。**たまたま今は同じだが、将来別々に変わるもの**を無理に共通化すると、かえって変更しづらくなります（過度な DRY）。意味的に同じものだけをまとめましょう。

## 2. わかりやすい命名

`data`・`temp`・`flag` のような曖昧な名前を、意図が伝わる名前に変えます。命名はコードの読みやすさに最も効きます。

```text
（before）              （after）
d        →            daysUntilExpiry
res      →            apiResponse
flag     →            isValidUser
```

良い名前は「中身を読まなくても何を表すか分かる」名前です。変数・関数・クラスすべてに当てはまります。

> [!TIP]
> 命名を変えるときは、その変数や関数を **参照しているすべての箇所**を同時に更新する必要があります。手作業では漏れが出やすいため、エディタや AI ツールのリネーム機能（参照ごと一括で変更）を使うと安全です。

## 3. 関数の抽出（長い関数の分割）

長すぎる関数を、意味のある単位の小さな関数に分割します。

```text
（before: 1つの関数に詰め込み）
function process(order) {
  // 入力検証（10行）
  // 金額計算（15行）
  // 保存（10行）
}

（after: 責務ごとに抽出）
function process(order) {
  validate(order);
  const total = calculateTotal(order);
  save(order, total);
}
```

分割の単位は「処理のまとまり ＝ 1 つの責務」です。「この部分は何をしているか」を一言で説明できるなら、それは抽出候補です。

> [!NOTE]
> コメントで区切られた塊は、関数化のよいサインです。「`// 金額計算` というコメント＋その下の処理」は、`calculateTotal()` という名前の関数にすれば、コメントなしで意図が伝わります。

## 4. 条件分岐の整理

深くネストした `if` や複雑な条件式を、読みやすく整理します。代表的なのが **早期 return（ガード節）** です。

```text
（before: ネストが深い）
function process(user) {
  if (user) {
    if (user.isActive) {
      // 本処理
    }
  }
}

（after: 早期returnでフラットに）
function process(user) {
  if (!user) return;
  if (!user.isActive) return;
  // 本処理
}
```

条件を満たさないケースを先に `return` で弾くことで、本処理のネストが浅くなり、読みやすくなります。

## パターン早見表

| パターン | 対象 | 要点 |
| --- | --- | --- |
| 重複の排除 | コピーされたロジック | 意味が同じものだけ共通化（過度な DRY に注意） |
| 命名の改善 | 曖昧な変数・関数名 | 意図が伝わる名前に、参照ごとリネーム |
| 関数の抽出 | 長い関数 | 責務単位で分割 |
| 条件分岐の整理 | 深いネスト | 早期 return でフラットに |

## やりすぎない

リファクタリングで最も多い失敗は **「やりすぎ」** です。すべてを完璧に整えようとすると、差分が巨大化し、振る舞いを変えるリスクも上がります。

- **1 回のリファクタリングは 1 つの目的に絞る**
- **将来を見越した過剰な抽象化を避ける**（YAGNI: You Aren't Gonna Need It）
- 大きな改善は、**小さなリファクタリングの積み重ね**で達成する

> [!IMPORTANT]
> パターンはあくまで道具です。「適用できるから適用する」のではなく、「**読みやすく・変更しやすくなるから**適用する」——目的を見失わないことが、良いリファクタリングの条件です。

## まとめ

- リファクタリングは **重複排除・命名改善・関数抽出・条件整理** の組み合わせで大半が片付く
- 重複排除は **意味が同じものだけ**——過度な DRY は逆効果
- 命名のリネームは **参照ごと一括**で行うと安全
- 関数抽出は **責務単位**で。条件整理は **早期 return** でフラットに
- 最大の失敗は **やりすぎ**。1 回 1 目的に絞り、小さく積み重ねる
