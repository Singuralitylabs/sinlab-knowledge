# デバッグとは（原因特定と修正）

デバッグとは、プログラムの誤った振る舞い（バグ）を正す作業です。多くの人は「コードを直すこと」だと考えますが、デバッグの本体は **「なぜ起きているかを突き止めること」**——原因特定にあります。本ページでは、デバッグを支える最も基本的な考え方を、ツールに依存しない普遍的な原則として解説します。

> [!NOTE]
> このページは原理原則を扱います。AI ツール（Claude Code・Cursor など）を使って実際にデバッグを進める方法は、[AIによるデバッグとリファクタリング](/themes/04-ai-driven-development/03-development-practice/ai-debugging-refactoring) を参照してください。

## このページで学べること

- デバッグは「修正」ではなく **「原因特定」** が本体であること
- バグ修正の **2 つの段階**（原因特定 → 修正）
- **症状（symptom）** と **根本原因（root cause）** の違い
- 「とりあえず動けばいい」修正がなぜ危険か

## デバッグの本体は「原因特定」

バグ修正は、おおまかに次の 2 段階に分かれます。

1. **原因特定** — なぜ問題が起きているのかを突き止める（調査）
2. **修正** — 特定した原因を取り除く（実装）

多くの人が「修正」に注目しますが、難しいのは圧倒的に **原因特定**です。原因さえ分かれば、修正は数行で済むことがほとんどです。逆に、原因を取り違えたまま修正しても、バグは消えません。

| 段階 | 問い | 難しさ |
| --- | --- | --- |
| 原因特定 | なぜ起きているのか？ | 高い（ここが本番） |
| 修正 | どう直すか？ | 低い（原因が分かれば自明なことが多い） |

> [!IMPORTANT]
> 「とりあえず動くように直す」という発想は、原因特定を飛ばして修正に走る行為です。これは後述する「症状の隠蔽」につながり、問題を別の場所に先送りします。**まず原因、それから修正**の順序を守りましょう。

## 症状と根本原因

バグには「目に見える症状」と「その奥にある原因」があります。両者を区別することが、デバッグの出発点です。

| | 症状（symptom） | 根本原因（root cause） |
| --- | --- | --- |
| 意味 | 表面に現れる困った現象 | 症状を引き起こしている本当の原因 |
| 例 | 画面がエラーで真っ白になる | API レスポンスの形式変更に追従できていない |
| 対処 | エラーを握りつぶして空表示にする | レスポンスを検証し、変更を検知できるようにする |
| 結果 | 一時的に見た目は直るが、データは欠落 | 問題の発生源そのものを解消 |

症状だけを潰すと、**原因は残ったまま別の場所で再噴出**します。デバッグのゴールは「症状を消す」ことではなく「原因を取り除く」ことです。

### 「動くコード」と「正しいコード」は違う

エラーが消えても、それが正しい状態とは限りません。たとえば例外を握りつぶせば「エラーは出なくなる」ものの、本来処理されるべきデータが失われているかもしれません。

> [!CAUTION]
> 「エラーが消えた」だけで満足しないこと。**なぜ消えたのかを説明できる**状態が、本当に直った状態です。説明できないなら、症状を偶然隠しただけかもしれません。

## デバッグの基本姿勢

これらを踏まえると、デバッグの基本姿勢は次のようにまとめられます。

- **修正より先に原因を特定する** — 急いでいるときほど守る
- **症状でなく根本原因を直す** — 表面を隠す対処は問題を先送りする
- **「なぜ直ったか」を説明できる状態にする** — 偶然の解消を「解決」と勘違いしない

これらは特別なテクニックではなく、どんな言語・ツールでも通用する普遍的な原則です。次のページからは、この姿勢を実際の手順——再現・根本原因分析・再発防止——に落とし込んでいきます。

## まとめ

- デバッグの本体は **「修正」ではなく「原因特定」**。原因が分かれば修正は容易なことが多い
- バグには **症状** と **根本原因** があり、潰すべきは根本原因
- 症状だけを隠す対処は、原因を別の場所に先送りする
- 「エラーが消えた」ではなく **「なぜ消えたか説明できる」** 状態がゴール
