# 根本原因分析（症状から原因へ）

再現できたら、次は「なぜ起きるのか」を突き止めます。表面の症状を追うだけでは、本当の原因にはたどり着けません。本ページでは、症状の奥にある **根本原因（root cause）** を論理的に掘り下げる方法——仮説検証ループと 5 Whys——を解説します。

## このページで学べること

- **仮説検証ループ**（観察 → 仮説 → 検証 → 学習）の回し方
- **5 Whys** で原因を深掘りする方法
- 推測ではなく **証拠（実際の値）** で確かめる重要性
- **回避策（workaround）** と **根本対処（fix）** の区別

## 仮説検証ループを回す

優れたデバッグは、当てずっぽうの修正ではなく **仮説 → 検証 → 学習** の繰り返しです。

1. **観察** — 症状・エラー・ログから事実を集める
2. **仮説** — 「○○が原因ではないか」と候補を立てる
3. **検証** — ログ追加・値の確認・最小再現で仮説を確かめる
4. **学習** — 当たれば原因確定、外れれば次の仮説へ

重要なのは、**修正に走る前に仮説を立てる**ことです。仮説なしの「とりあえず変えてみる」を繰り返すと、たまたま症状が消えても原因が分からず、再発します。

> [!CAUTION]
> 「コードを読んだ推測」は、あくまで仮説です。推測で原因を断定せず、**実際の値をログで確認する**まで原因が確定したと考えないようにしましょう。証拠 > 推測です。

## 5 Whys で深掘りする

根本原因にたどり着く古典的な手法が **5 Whys**（なぜを繰り返す）です。症状から出発して「なぜ？」を繰り返し、真の原因まで掘り下げます。

```text
- なぜ画面が落ちる? → user.profile が undefined だから
- なぜ undefined? → API が profile を含まないレスポンスを返したから
- なぜ含まない? → 認証トークン切れ時に 401 ではなく空オブジェクトを返す仕様だから
- なぜ空を返す? → エラーハンドリングが API 層で握りつぶされているから
- なぜ握りつぶす? → 過去に「エラーで落ちる」のを場当たり的に隠した経緯がある

→ 根本原因: API 層のエラーハンドリングが、認証切れを正しく伝播していない
```

この例では、表面の `user.profile` チェックを足すだけでは本質的な解決になりません。深掘りすると **真に直すべき箇所**（API 層のエラーハンドリング）が見えてきます。

> [!TIP]
> 「5 回」はあくまで目安です。重要なのは **「これ以上掘っても変わらない」ところまで掘る**こと。逆に、掘りすぎて「人間のミス」「予算がない」など対処不能な領域に達したら、一段戻って **対処可能な原因** を選びます。

## 回避策と根本対処を区別する

現実には、すぐ根本対処できない場合もあります。その際は **「今は回避策」「後で根本対処」を明示的に区別**することが重要です。

| 区分 | 内容 | 扱い |
| --- | --- | --- |
| 回避策（workaround） | 症状を一時的に抑える応急処置 | TODO や issue で残し、後で根本対処する |
| 根本対処（fix） | 原因そのものを取り除く | これが本来のゴール |

> [!WARNING]
> 回避策を入れる場合は、**「なぜ回避策なのか」「本来どう直すべきか」をコメントや issue に必ず残す**こと。記録しないと、回避策が恒久化して技術的負債になります。「一時的な対処」は、記録がなければ「恒久的な負債」に変わります。

## まとめ

- 根本原因分析は **仮説 → 検証 → 学習** のループで進める
- 修正に走る前に **仮説を立てる**。推測でなく **実際の値（証拠）** で確かめる
- **5 Whys** で「なぜ」を繰り返し、真に直すべき箇所まで掘り下げる
- すぐ直せない場合は **回避策と根本対処を区別**し、回避策の背景を必ず記録する
