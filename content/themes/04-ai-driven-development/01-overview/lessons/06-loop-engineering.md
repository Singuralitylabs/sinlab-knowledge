# ループエンジニアリング

AI コーディングエージェントの成果を決めるのは、1 回の生成がどれだけ賢いかではありません。**行動したあと、環境からのフィードバックをどう受け取り、次の一手をどう決めるか** です。テストが赤なら直し、ビルドが通るまで繰り返す——この「回り方」を意図して設計する技術が **ループエンジニアリング** です。

コンテキストエンジニアリングが「何を見せるか」、ハーネスエンジニアリングが「どんな環境で動かすか」を扱うのに対し、本レッスンは **どう回らせるか** に焦点を当てます。

## このページで学べること

- **ループエンジニアリング** の定義と、コンテキスト / ハーネスとの 3 部作関係
- Claude Code が公式に定義する **エージェンティックループ**（コンテキスト収集 → 行動 → 検証）の仕組み
- 自己修正が効くために必要な **検証手段（フィードバック）** の役割
- ループを構成する **検証手段 / 完了条件 / 境界** の 3 要素
- AI の自己修正（内側）と、人間レビュー・CI・PR（外側）の接続
- 本サイトの記事執筆で使っている完了条件の実例と、よくあるアンチパターン

## ループエンジニアリングとは何か

**ループエンジニアリング** とは、AI が自律的に「行動 → 検証 → 修正」を繰り返すフィードバックループを、目的を持って設計する技術です。対象はプロンプトの言い回しそのものではなく、**何を検証し、どこで止め、どこで人間に返すか** です。

このレッスンで扱うループは、[AI開発の基本ループ](/themes/04-ai-driven-development/03-development-practice/ai-development-loop) とは層が違います。あちらは人間側の工程——計画 → 実装 → デバッグ → リファクタリング → レビュー——の回し方です。本レッスンは、その各工程の内側で **AI がツールを使って自律的に回すループ** を扱います。

概論モジュールの 3 本は、次のように積み上がります。

| レッスン | 設計する対象 | 中心の問い |
| --- | --- | --- |
| [コンテキストエンジニアリング](/themes/04-ai-driven-development/01-overview/context-engineering) | AI に見せる情報 | 何を前提として考えさせるか |
| [ハーネスエンジニアリング](/themes/04-ai-driven-development/01-overview/harness-engineering) | AI の動作環境 | どんな道具と権限で動かすか |
| ループエンジニアリング（本ページ） | 反復の仕組み | どう検証し、いつ止めるか |

ハーネスが「馬具」、モデルが「馬」だとすれば、ループは **走路とゴールと審判** です。道具が揃っていても、ゴール判定がなく、何周でも走れるコースでは、速さは成果に結びつきません。

> [!NOTE]
> 「ループエンジニアリング」は、コンテキスト / ハーネスと並べて設計対象を切り出すための呼称です。Claude Code の公式用語は **エージェンティックループ**（agentic loop）と **検証ループ**（verification loop）です。本レッスンでは公式のループ構造を土台に、設計観点を 3 要素へ整理します。

## エージェンティックループの仕組み

Claude Code の公式ドキュメントは、タスクを次の 3 相で進めると説明しています。

1. **コンテキスト収集（gather context）** — ファイルを読む、エラーログを取る、仕様や関連コードを探す
2. **行動（take action）** — コードを編集する、コマンドを実行する、外部ツールを呼ぶ
3. **検証（verify results）** — テスト・型チェック・lint・ビルド・スクリーンショットなどで結果を確かめる

この 3 相は厳密な順番というより、必要に応じて混ざり合います。質問だけなら収集で終わることもありますし、バグ修正では 3 相を何度も往復します。各ツール実行の結果が次の判断材料になり、何十手もつなぎながら軌道修正します。

![エージェンティックループ：コンテキスト収集 → 行動 → 検証 → 繰り返し（または完了）](/content-assets/04-ai-driven-development/01-overview/images/loop-engineering/agentic-loop.svg)

Anthropic の [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) は、エージェントを「環境からのフィードバックを手がかりに、LLM が自分でツールを選んで回すループ」と捉えます。各ステップで必要なのは、モデルの自己申告ではなく、**ツール結果やコード実行といった環境からの根拠（ground truth）** です。タスクは完了で終わるのが基本ですが、最大反復回数のような停止条件を置くことも一般的だとしています。

Claude Code の用語では、この実行サイクルが **エージェンティックループ** です。拡張ポイントである Hooks / Skills / MCP は、このループの特定の相に差し込む部品です。[Hooks](/themes/04-ai-driven-development/02-claude-code/hooks) の記事が言う「エージェントループ」も、同じ実行サイクルを指します。

> [!TIP]
> あなたもループの一部です。公式ドキュメントは、途中で割り込んで方向を変えたり、追加の文脈を渡したりできると明記しています。自律は「放置」ではなく、**必要なときに人間が舵を取れる状態** です。

## なぜループ設計が効くのか

自己修正は、検証手段があるときにだけ機能します。Claude Code のベストプラクティスは、これを端的に書いています。**Claude は「終わったように見える」ところで止まります。** 実行可能なチェックがなければ、「見た目の完了」が唯一の信号になり、間違いに気づく役割は人間に残ります。

検証のないループが量産するのは、自信のある間違いです。テストを走らせず「直しました」と報告する、型エラーを読まずに次のファイルへ進む、画面を見ずに UI を「整えた」と言う——いずれも、フィードバックが会話の外にある状態です。

逆に、パス / 失敗が返るチェックを渡すと、ループは自分で閉じます。作業する、チェックを走らせる、結果を読む、通るまで直す。公式用語の **検証ループ** は、この「1 回で止めず、チェックが通るまで反復する」形を指します。無人実行や `/goal` が前提にするのも、この検証ループです。

[開発ワークフローはどう変わるか](/themes/04-ai-driven-development/01-overview/workflow-changes) で見た「生成 → 評価 → 修正」の螺旋は、ループ設計の外側からの見え方です。本レッスンは、その螺旋を **検証可能な信号で回す** 側の話です。

## ループを構成する 3 要素

回り方を設計するときは、次の 3 つをセットで決めます。どれか 1 つ欠けても、ループは止まりません。あるいは、止まったつもりで品質だけが落ちます。

| 要素 | 役割 | 例 |
| --- | --- | --- |
| ① 検証手段 | 環境からパス / 失敗を返す | テスト、型チェック、lint、ビルド、スクリーンショット比較 |
| ② 完了条件 | 「終わった」の判定基準 | Definition of Done、`/goal` の条件、チェックリスト |
| ③ 境界 | 無限反復と暴走を防ぐ枠 | 最大反復回数、エスカレーション、人間の確認ポイント |

### ① 検証手段

エージェントが自分で実行でき、会話に戻せる信号が必要です。公式ドキュメントが挙げる例は、テストスイート、ビルドの終了コード、リンター、フィクスチャとの diff、デザインと比較するブラウザのスクリーンショットです。

速いほど内側のループを多く回せます。遅い E2E だけを検証にすると、1 周が長くなり、修正の仮説を試す回数が減ります。

### ② 完了条件

検証手段は「今の一手が正しいか」を返し、完了条件は「タスク全体が終わったか」を返します。テストが 1 本通っても、レビュー未了・ドキュメント未更新なら未完了、という切り分けです。

Claude Code では、プロンプトに「テストを走らせて通るまで直して」と書く、セッション全体を [`/goal`](https://code.claude.com/docs/en/goal) で拘束する、[Stop hook](https://code.claude.com/docs/en/hooks#stop) で決定論的に止める、といった段階があります。セットアップが増えるほど、人間が毎回確認しなくても止まりやすくなります。

### ③ 境界

完了条件があっても、到達できない場合があります。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) も、最大反復回数のような停止条件を置くのが一般的だとしています。Stop hook でターン終了をブロックする場合も、連続ブロックが続くとハーネス側が上書きして止めます（Claude Code では 8 回。公式ベストプラクティスの [Give Claude a way to verify its work](https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work) に記載）。

境界の典型は次の 3 つです。

- **回数** — レビュー往復の上限、同一エラーでの再試行回数
- **エスカレーション** — 上限に達したら人間へ渡し、自動ループを終える
- **確認ポイント** — 破壊的操作、外部公開、`main` へのマージは人間が承認する

> [!IMPORTANT]
> 3 要素は独立ではありません。検証が曖昧だと完了条件は自己申告になり、境界がないと「もう少し直せそう」が終わりません。**何を測り、何をもって終わり、何回で人に返すか** を先に書くのがループ設計です。

## 検証手段の与え方

検証は、速く、決定的で、エージェントが読めることが重要です。

| 観点 | 効く理由 | 向いている手段 |
| --- | --- | --- |
| 高速 | 内側のループを短く回せる | ユニットテスト、型チェック、lint |
| 決定的 | パス / 失敗が解釈で揺れない | 終了コード、スナップショット diff |
| 可読 | 失敗理由が次の行動に使える | 失敗したテスト名、型エラー、lint の該当行 |

テスト駆動開発との相性が良いのは、この 3 点が揃いやすいからです。先にテスト（または型・lint）を置き、実装をエージェントに任せ、赤をフィードバックにして直させる。人間は「何が正しいか」をテストで固定し、エージェントは「どう直すか」をループで探します。

UI ではスクリーンショット比較が検証手段になります。見た目の好みを文章だけで伝えるより、基準画像との差分をエージェント自身に取らせるほうが、内側のループが閉じます。

> [!TIP]
> 「直して」ではなく、「このコマンドを実行し、失敗したら原因を読んで直して、通るまで繰り返して」と、**検証コマンドごと渡す** のが基本です。チェックの実行を人間が肩代わりすると、内側のループは回りません。

> [!CAUTION]
> 検証を通すためにテストを弱める、断言を外す、エラーを握りつぶす——これらはループを壊します。スピードのためにフィードバックを歪めると、以降の反復は誤った「緑」を正解だと思い込みます。

## 内側のループと外側のループ

エージェントの自己修正だけを高速にしても、成果物の責任は残りません。内側と外側を分けて接続します。

```text
内側（AI の自己修正）
  コンテキスト収集 → 行動 → 検証 → 繰り返し
        ↑ テスト / 型 / lint / ビルド

外側（人間とチームの検証）
  レビュー → CI → PR 承認 → マージ
        ↑ 差分の妥当性 / 要件 / 運用影響
```

- **内側** — エージェントがツールで回すループ。速い・安い・何度でも試せる。失敗してもチェックポイントや git で戻せる範囲が対象
- **外側** — 人間のレビュー、CI、プルリクエスト。[開発ワークフローはどう変わるか](/themes/04-ai-driven-development/01-overview/workflow-changes) のレビュー責任や、[AI開発の基本ループ](/themes/04-ai-driven-development/03-development-practice/ai-development-loop) の「判断は人間」がここに相当する

内側を厚くすると、外側に上がる差分の粗さは減ります。ただし内側の緑は「決めたチェックを通った」ことしか保証しません。要件の妥当性、長期の保守性、セキュリティの判断は外側に残します。

ハーネス側の部品も、この二層にまたがります。`PostToolUse` の format / lint は内側を速くします。permission mode や危険操作の確認は、内側が外側へエスカレーションする境界です。

## 実例: 本サイトの記事執筆ループ

本サイトの学習記事を追加するときは、issue に **完了条件（ループエンジニアリング）** を書き、自動レビューと修正の往復で記事をフィックスします。3 要素は次のように対応します。

| 要素 | 記事執筆での具体化 |
| --- | --- |
| 検証手段 | `bun run lint` / `bun run typecheck` / `bun test` / `bun run check:content`、公式ドキュメントでの事実の裏取り、記事内リンクの生存確認 |
| 完了条件 | (1) issue の構成案をすべて満たす (2) CI の 5 ワークフローが成功する (3) 事実を公式ソースで裏取りしリンクが有効 (4) 別セッションのレビューで must-fix がゼロ |
| 境界 | レビューと修正の往復は最大 3 回。3 回でも解消しなければ未解消一覧を issue に残して人間へエスカレーション。`main` へのマージは人間が行う |

レビュー観点も先に固定しています。事実の正確性、文体・構成規約、リンクの有効性、既存レッスンとの重複です。nice-to-have の改善提案は完了を妨げません。完了条件が「もっと良くできそう」に侵食されないようにするためです。

この運用は、内側（エージェントが lint と事実確認を回す）と外側（人間が PR を承認する）を明示的に分けています。検証手段をコマンドにし、完了条件を 4 項目に数え、往復回数で境界を切る——本レッスンの 3 要素を、記事という成果物に適用した形です。

> [!NOTE]
> 同じ型はコーディングタスクにも使えます。「テストと型チェックが通る」「PR 説明が差分と一致する」「セキュリティレビューで must-fix がない」を完了条件にし、再試行回数と人間承認を境界にする、という書き方です。

## よくあるアンチパターン

- **検証手段なしの「もう一回やって」** — 失敗の信号がなく、同じ自信過剰な出力が繰り返される。先に実行可能なチェックを渡す
- **完了条件のない無限磨き込み** — 「もう少し綺麗に」が終わりにならない。must-fix と任意改善を分け、前者だけを完了条件にする
- **テストを弱めて green にする** — 内側のループは回っているように見えるが、信号が嘘になる。失敗しているテストを直すか、テストの意図を先に合意する
- **境界のない放置** — 回数上限もエスカレーションもなく回し続ける。トークンと時間を消費し、文脈も劣化する
- **内側と外側の混同** — CI が緑なら要件も満たした、あるいは逆に、すべての判断を人間が毎回見る。層を分け、内側で機械的に潰せるものは内側へ寄せる
- **人間が検証を肩代わりする** — エージェントにテストを走らせず、人間がブラウザで確認して「違う」とだけ返す。フィードバックが会話に乗らず、内側が回らない

> [!WARNING]
> 「もう一度生成させる」はループ設計ではありません。**同じ入力でサイコロを振り直しているだけ** です。何が失敗で、何をもって成功とし、何回で人に返すかを先に固定してください。

## まとめ

- ループエンジニアリング ＝ **AI の「行動 → 検証 → 修正」を設計する** 技術
- 成果を決めるのは 1 回の生成の賢さではなく、**ループの回り方**
- 公式のエージェンティックループは **コンテキスト収集 → 行動 → 検証**。拡張機能はこのループに差し込む
- 自己修正には **環境からの検証信号** が必須。検証のないループは自信過剰な間違いを増やす
- 設計の 3 要素は **検証手段 / 完了条件 / 境界**
- 検証は **高速・決定的・可読**。テスト駆動との相性が良い
- **内側**（AI の自己修正）と **外側**（レビュー・CI・PR）を分けて接続する
- 本サイトの記事執筆は、4 項目の完了条件と往復 3 回の境界で、この型を運用している
