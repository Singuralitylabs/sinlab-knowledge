# 生成AIベンチマークの読み方

新しいモデルや機能が発表されるたびに、「SWE-bench Verified で 82%！」「GPQA で過去最高スコア！」といった数字が華々しく紹介されます。しかし、その数字が **何を・どんな条件で・誰が測ったのか** を知らないまま受け取ると、しばしば判断を誤ります。

本章では、個々のスコアの大小に一喜一憂するのではなく、**ベンチマークを「読む」ための視点**を整理します。具体的な順位は週単位で入れ替わるため、ここでは順位の暗記ではなく、**いつ見ても通用する読み方**を身につけることを目標とします。

## このページで学べること

- ベンチマークの数字が独り歩きしやすい理由と、よくある **3 つの誤解**
- モデルを大枠で捉える **「知能・速度・コスト」の 3 軸** と、指標を整理する **3 段の地図**
- **目的別に、どの指標を「基準」に検証すればよいか**（用途 → 主指標の対応）
- スコアを左右する **測定条件**（pass@1、多数決、推論モードなど）の読み方
- データ汚染・飽和など、ベンチマーク特有の **落とし穴**
- 用途に応じた **比較サイトの使い分け**
- 比較表を見るときの **実践チェックリスト**

## ベンチマークとは / なぜ「見方」が重要か

ベンチマークとは、**特定の能力を、決められた問題セットで数値化した試験**です。人間でいう「TOEIC のスコア」や「模試の偏差値」に近く、あくまで **ある側面を切り取った代理指標** にすぎません。

数字だけを単純比較すると、次のような誤解に陥りがちです。

- **誤解 1: 「MMLU 92% > 90% だから新モデルの方が賢い」** — MMLU のように上位モデルが軒並み高得点に達した指標（= **飽和**）では、数 % の差にほとんど意味がありません。
- **誤解 2: 「公式発表のスコアが一番高いから最強」** — 開発元の **自己申告スコア** は、自社に有利な測定条件で出されていることがあります。
- **誤解 3: 「総合ランキング 1 位を選べば万能」** — ある試験の 1 位が、別の試験では 3 位以下ということは日常的に起こります。

そこで本章が一貫して伝えたい核心はこれです。

> [!IMPORTANT]
> ベンチマークは、単一スコアの大小ではなく **「カテゴリ × 測定条件 × 出典の信頼性」** の 3 点で読む。

## まず大枠で捉える — 「知能・速度・コスト」の 3 軸

細かいベンチマークに入る前に、まず **モデル選びの実務で効く 3 つの軸** を押さえると全体像がつかめます。新モデルが出ても、結局この 3 軸（＋人間の体感）に話は集約されます。

| 軸 | 問い | 代表的な見方・指標 |
| --- | --- | --- |
| 知能 | どれだけ賢いか | 集約スコア（Artificial Analysis の Intelligence Index など）／用途別ベンチマーク |
| 速度 | どれだけ速いか | スループット（1 秒あたり生成トークン数）／初回応答までの時間（TTFT） |
| コスト | いくらかかるか | 100 万トークンあたりの入力・出力単価 |
| 体感 | 人間が好むか | LMArena の Elo 系レーティング（Arena Score） |

![モデル選びの4軸：知能・速度・コスト効率（＋体感）のバランスで見る](/content-assets/04-ai-driven-development/01-overview/images/benchmarks/three-axes.svg)

世の中で紹介される無数のベンチマーク（SWE-bench、GPQA など）は、ほとんどがこの中の **「知能」軸を細かく分解したもの** です。「賢さ」と一口に言っても、知識が豊富なのか、推論が得意なのか、コードが書けるのか —— 中身は能力ごとに分かれます。

> [!CAUTION]
> 「知能」軸ばかりに注目しがちですが、実務では **速度とコストで脱落する** ことが珍しくありません。どれだけ賢くても、遅すぎる・高すぎるモデルは使い続けられません。最初から 3 軸セットで見る癖をつけましょう。

### 指標は「3 段の地図」で整理する

ベンチマークは数十種類ありますが、**粒度の 3 段** で捉えると迷いません。上の段ほど「ざっくり全体感」、下の段ほど「特定能力の詳細」です。

![指標の3段の地図：総合・集約指標 → 能力カテゴリ → 個別ベンチマークへと上から下へ絞り込む](/content-assets/04-ai-driven-development/01-overview/images/benchmarks/three-tier-map.svg)

1. **総合・集約指標（全体感をつかむ）** — 多数の試験を 1 つの数字にまとめたもの。Artificial Analysis の Intelligence Index や、人間の選好を表す LMArena の Elo 系スコアなど。**まずここで当たりをつける**。
2. **能力カテゴリ（強み・弱みを見る）** — 知識・推論・数学・コーディング・エージェント…といった大分類。**用途に直結する**。
3. **個別ベンチマーク（詳細を詰める）** — SWE-bench Verified、GPQA など具体的な試験。**最終的な裏取り**に使う。

> [!TIP]
> 実務での流れは **「① 総合指標で 2〜3 候補に絞る → ② 自分の用途のカテゴリで比べる → ③ 個別ベンチマークで裏取り」** という上から下への絞り込みが効率的です。いきなり個別ベンチマークの細かい数字から入らないのがコツ。

## 目的別 — どの指標を「基準」に検証するか

ベンチマークは数多くありますが、**自分の目的を決めれば、基準にすべき主指標はほぼ 1〜2 個に絞れます**。新しいモデルを評価するときは、まず下の表で **自分の目的の「基準にする主指標」と「参照サイト」** を確認し、それを軸に比べてください。各サイトの特徴は [参照サイトの特徴](#参照サイトの特徴と裏取り) にまとめています。

| 目的（やりたいこと） | 基準にする主指標（補助指標） | 参照サイト | 検証のポイント |
| --- | --- | --- | --- |
| コーディング・実装支援 | SWE-bench Verified（LiveCodeBench / Aider Polyglot / Terminal-Bench） | [SWE-bench 公式](https://www.swebench.com/) / [Artificial Analysis](https://artificialanalysis.ai/) | 実在の GitHub issue を解けるか。自分の言語・スタックに近いか |
| 自律エージェント（ツール使用） | τ²-bench（GAIA） | [GAIA 公式](https://huggingface.co/spaces/gaia-benchmark/leaderboard) / [Artificial Analysis](https://artificialanalysis.ai/) | 複数ステップのタスク完遂率・ツール呼び出しの正確さ |
| 難しい知識・推論 | GPQA Diamond（HLE / ARC-AGI-2） | [Artificial Analysis](https://artificialanalysis.ai/) / [Epoch AI](https://epoch.ai/)（GPQA Diamond）。[ARC-AGI](https://arcprize.org/) は公式 | 飽和した MMLU ではなく難問指標で差を見る |
| 数学・論理 | AIME（FrontierMath） | [Artificial Analysis](https://artificialanalysis.ai/) / [Epoch AI](https://epoch.ai/) | 段階的推論。多数決（cons@k）など測定条件に注意 |
| 長文脈の正確さ | RULER（Needle-in-a-Haystack） | 各社の公式レポート（[RULER](https://github.com/NVIDIA/RULER) は評価コード・手法） | 宣伝の最大トークン数でなく「実効的に拾える精度」を見る。中央集権的な順位表はない |
| 文章・対話の体感 | LMArena（Elo） | [LMArena](https://lmarena.ai/) | 人間の選好。差が小さいときは誤差区間を見る |
| 日本語性能 | Nejumi Leaderboard | [Nejumi（W&B, 最新版）](https://wandb.ai/wandb-japan/llm-leaderboard3/reports/Nejumi-LLM-Leaderboard3--Vmlldzo4NDkwODEy) | 英語ベンチが高くても日本語性能は別物 |
| 画像理解（マルチモーダル） | MMMU（MathVista） | [MMMU 公式](https://mmmu-benchmark.github.io/) / [Artificial Analysis](https://artificialanalysis.ai/) | 画像とテキストを統合して理解できるか |

> [!TIP]
> 迷ったら、自分の目的の **「基準にする主指標」を 1 つだけ**、その **参照サイト** で見れば十分なことが多いです。補助指標は、主指標で差がつかないときや、用途が複合的なとき（例: コードを書く自律エージェント）に足して見ます。

なお、上の表に古くからの有名指標（MMLU・GSM8K・HumanEval など）が「基準」として出てこないのは、**飽和や汚染で差がつかなくなった** からです。どの指標が主役かは **おおむね 1〜数年** で入れ替わります（理由は後述の [ベンチマークの落とし穴](#ベンチマークの落とし穴) を参照）。

> [!NOTE]
> **測定条件でスコアは動きます**（`pass@1` か多数決 `cons@64` か、`thinking` の有無）。ただし標準化サイトは全モデルを同一条件で測るので、自分で気にするのは主に **各社の発表値どうしを比べるとき**だけ。その条件は技術レポートの脚注にあります。

## ベンチマークの落とし穴

ベンチマークには構造的な弱点があります。代表的なものと対策を押さえておきましょう。

| 落とし穴 | 内容 | 対策 |
| --- | --- | --- |
| データ汚染（contamination） | 試験問題が訓練データに混入し、暗記で高得点になる | 問題を定期更新する LiveBench 等を併用 |
| 飽和（saturation） | 上位が皆高得点で差が出ない（MMLU など） | より難しい後継指標を見る |
| 自己申告 vs 第三者検証 | 公式値は有利な条件で測られがち | 独立評価サイトで照合する |
| チェリーピッキング | 勝てる試験だけを資料に載せる | 複数サイト・複数指標で確認 |
| 知能だけ見てコスト/速度を無視 | 1 位でも高価・低速なら実務で使えない | 価格・速度・文脈長も同時に見る |

とりわけ **飽和と汚染** は、指標の主役が入れ替わる原因になります。古い有名指標（MMLU・GSM8K・HumanEval）が差を生まなくなる一方で、評価の関心は「一問一答のチャット」から **「自律的にコードを書き、ツールを使うエージェント」** へ移り、SWE-bench Verified やエージェント系が主戦場になりました。

![ベンチマークのライフサイクル：旧指標は飽和し、新しい難問指標へ主役が移る](/content-assets/04-ai-driven-development/01-overview/images/benchmarks/benchmark-lifecycle.svg)

> [!NOTE]
> 「動く」には 2 つの速さがあります。**モデルの順位は数週間〜数ヶ月** で入れ替わる一方、**ベンチマーク自体の交代は 1〜数年** とずっと遅い（新指標は作問・検証・普及に時間がかかるため。例: τ²-bench → τ³-bench）。だから特定の指標を覚えるより、**「今どれが飽和していないか」を見る目** を持つことが大事です。

## 参照サイトの特徴と裏取り

上の早見表の「参照サイト」列に出てくるサイトの特徴です。それぞれ性質が違うので、用途に合わせて使い分けます。大きく **第三者による標準化評価**（測定条件を固定・開示してくれる）と **手軽な比較表** に分かれます。

![参照サイトの3分類：標準化評価／公式リーダーボード／アグリゲーターと信頼度](/content-assets/04-ai-driven-development/01-overview/images/benchmarks/site-trust-map.svg)

**第三者・標準化評価（裏取りの軸にする）**

- **[Artificial Analysis](https://artificialanalysis.ai/)** — 知能・価格・速度を同一条件で横断比較。コストを含めた実務判断に向く。
- **[LiveBench](https://livebench.ai/)** — 汚染対策として問題を定期更新する設計（毎月更新を標榜）。Abacus.AI と大学研究者（NYU など）による共同運営。ただし公開ボードへの反映が遅れることがあるため、**最終更新日と掲載モデルを必ず確認** して使う。
- **[LMArena](https://lmarena.ai/)** — 人間の選好を表す Elo 系スコア（現在は Bradley–Terry ベースの Arena Score）。「体感の良さ」を測れる数少ない指標。
- **[Epoch AI](https://epoch.ai/)** — 能力トレンドの長期分析・研究データ。
- 各ベンチマークの **公式リーダーボード**（[SWE-bench](https://www.swebench.com/)、[ARC-AGI](https://arcprize.org/)、[GAIA](https://huggingface.co/spaces/gaia-benchmark/leaderboard)、[MMMU](https://mmmu-benchmark.github.io/) など）— その指標の一次情報。表で「◯◯ 公式」と書いた場合はこれを指します。ただし **SWE-bench のような提出制のボードは、ベンダー発表より掲載が遅れる**点に注意（最新モデルが未提出で載っていないことがある）。なお [RULER](https://github.com/NVIDIA/RULER) は順位表ではなく **評価コード／手法のリポジトリ** で、長文脈スコアは各社のレポートに散在します。
- **[Nejumi Leaderboard（最新版）](https://wandb.ai/wandb-japan/llm-leaderboard3/reports/Nejumi-LLM-Leaderboard3--Vmlldzo4NDkwODEy)** — 日本語性能の定番（Weights & Biases 運営）。版が Neo / 3 / 4 と分かれているので、**最新版を開いているか**に注意（更新は月単位）。

**手軽な比較表（確認用、一次情報で裏取り前提）**

- **[Vellum LLM Leaderboard](https://www.vellum.ai/llm-leaderboard)** — 飽和指標を除いた非飽和ベンチマーク（GPQA Diamond / SWE-bench Verified / HLE / ARC-AGI 2 など）に、コスト・速度・文脈長を併記した、全体像をつかむのに便利なアグリゲーター。ただし数値はベンダー自己申告と独自計測の混在のため、**決定的な比較は一次情報か独立評価で裏取り** する。
- **[llm-stats.com](https://llm-stats.com/)** など他の集約サイトも同様で、見やすい反面、出典・更新頻度はサイトに依存します。**気になった数字は必ず一次情報や第三者評価で裏を取る** のが安全です。

> [!CAUTION]
> リーダーボードは **更新が止まっていることがあります**。提出制の公式ボード（SWE-bench など）はベンダー発表より遅れ、第三者ミラーは古いまま放置されることもあります。引用する前に **「最終更新日」と「掲載されている最新モデル」を必ず確認** しましょう。古いモデルが首位に見えるときは、たいてい新モデルが未提出・未反映なだけです。

## 比較表を見るときの実践チェックリスト

最後に、実際に比較表を前にしたときの手順を 7 ステップにまとめます。

1. **用途を決める** — コーディングか、チャットか、日本語か、エージェントか。これで見るべき指標が決まる。
2. **カテゴリ別に複数の指標を見る** — 単一スコアで判断しない。
3. **測定条件に注意する** — pass@1 か多数決か、推論モード（thinking）の有無。条件は技術レポート側にあり、標準化サイトなら固定済み。アグリゲーターで条件が不明なら一次情報で確認する。
4. **第三者評価で裏取りする** — 公式発表を鵜呑みにしない。
5. **コスト・速度・文脈長も同じ表で確認する** — 知能だけで選ばない。
6. **飽和した指標は無視する** — MMLU の数 % 差などに意味を持たせない。
7. **サイトの鮮度を確認する** — 最終更新日と掲載モデルを見る。提出制の公式ボードはベンダー発表より遅れることがある。

## まとめ

- ベンチマークは能力の一側面を切り取った **代理指標**。単一スコアの大小では判断しない。
- まず **「知能・速度・コスト（＋体感）」の 3 軸** で大枠をつかむ。賢さだけで選ばない。
- 指標は **3 段の地図**（総合指標 → 能力カテゴリ → 個別ベンチマーク）で整理し、**上から下へ絞り込む**。
- 指標には **重視度の濃淡** があり時間で入れ替わる。飽和・汚染した古い指標（MMLU 等）より、**いま飽和していない指標** を見る。
- 読むときの軸は **「カテゴリ × 測定条件 × 出典の信頼性」** の 3 点。
- 指標は用途別に地図を持つ（コーディング＝ SWE-bench Verified、体感＝ LMArena、日本語＝ Nejumi など）。
- pass@1 / 多数決 / 推論モードなど **測定条件をそろえて** から比較する。
- データ汚染・飽和・自己申告に注意し、**第三者評価（Artificial Analysis / LiveBench など）で裏取り** する。
- 順位は陳腐化するので、**読み方とサイトの使い分け** を資産として持つ。
