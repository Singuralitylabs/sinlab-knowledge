# ハーネスエンジニアリング

2026 年現在、AI コーディングの主戦場は **モデルそのもの** から、AI を取り囲む **動作環境（ハーネス）の設計** へと移っています。同じフロンティアモデルを使っていても、周辺の前提情報・ツール・権限・ワークフローをどう組み立てるかで、生産性は桁違いに変わります。本レッスンでは、その設計技術である **ハーネスエンジニアリング** を一段上の視点から束ねて整理します。

## このページで学べること

- **ハーネス** という概念の語源と、AI 文脈での意味
- なぜ「モデル選び」から「ハーネス設計」へ主戦場が移ったのか
- ハーネスを構成する **6 つの要素** と相互関係
- **モデル / ハーネス / プロジェクト** の 3 層モデルで設計を捉える視点
- 設計原則・アンチパターン・始め方ロードマップ

## ハーネスとは何か — 語源と比喩から

![馬具のハーネスと AI のハーネス：力を制御し安全に発揮させる装置という同じ構造](/content-assets/04-ai-driven-development/01-overview/images/harness-engineering/harness-metaphor.png)

「harness」は本来、馬具・登山具・安全帯など、**力を制御し、安全に発揮させるための装置**を指す言葉です。馬の力をそのまま放っておけば暴走しかねないものを、ハーネスを介すことで荷車を引かせたり方向を制御したりできるようになります。

AI コーディング文脈での **ハーネス** も同じ比喩で捉えられます。

- AI モデルそのものが「馬」 — 強力だが、放っておけば暴走したり、見当違いの仕事をしたりする
- 周辺の **コンテキスト・ツール・権限・ワークフロー一式** が「ハーネス」 — 力を意図した方向に向け、安全に成果に結びつける装置

つまりハーネスエンジニアリングとは、**AI モデルを取り囲む環境を、目的を持って設計する技術** のことです。

> [!NOTE]
> ハーネスは「制限」ではなく「方向付け」と捉えるのがポイント。馬具がない馬が速いわけではないように、適切なハーネスがない AI は本来の生産性を発揮できません。

## なぜ「モデル選び」から「ハーネス設計」へ移ったのか

数年前まで、AI コーディングの議論の中心は「どのモデルが賢いか」でした。しかし 2026 年現在、状況は大きく変わっています。

### 1. フロンティアモデルが横並びになった

Claude / GPT / Gemini といった主要モデルは、コーディングタスクにおいて実用的にはどれを選んでも同等の成果に到達できるレンジに入っています。「どれを使ってもそれなりに動く」状況になり、**モデル選択は差別化要因として効きにくく** なりました。

### 2. ボトルネックが「生成」から「制御と評価」へ移った

第 4 世代（ターミナル自律型）以降、AI は「コードを書く」だけでなく **タスクを自律的に完了させる** ようになりました。すると次に問題になるのは：

- 出力をどうレビュー・検証するか
- 危険な操作（force push、ファイル削除、外部 API 呼び出し）にどう境界を引くか
- 同じ作業を再現可能にどう蓄積するか

つまり、「賢く書かせる」よりも **「自律に任せた結果をどう制御し、信頼できる成果物にするか」** のほうが難しい問題になっています。

### 3. 差別化要因のシフト

```text
旧:「どのモデルを使うか」 が生産性を決める
新:「どう設計して使うか」 が生産性を決める
```

各世代の進化と「人間が AI に渡すもの」の変化については [主要ツールの登場と発展の系譜](/themes/04-ai-driven-development/01-overview/history) を参照してください。

## ハーネスを構成する 6 つの要素

ハーネスは単一の機能ではなく、複数の要素の組み合わせです。Claude Code を例に取ると、以下の 6 つに整理できます。各論ページで詳しく扱う構成要素の **位置付け** をここで束ねて理解してください。

![ハーネスを構成する 6 つの要素：AI モデルを中心にコンテキスト・MCP・サブエージェント・Skills・Hooks・権限が相互に作用する](/content-assets/04-ai-driven-development/01-overview/images/harness-engineering/harness-six-elements.png)

| # | 要素 | 役割 | 詳しくは |
| --- | --- | --- | --- |
| ① | コンテキスト設計 | AI に渡す前提情報を最適化 | [コンテキストエンジニアリング](/themes/04-ai-driven-development/01-overview/context-engineering) |
| ② | ツール拡張（MCP） | 外部サービス・DB・ブラウザを操作する手段を AI に与える | [MCP](/themes/04-ai-driven-development/02-claude-code/mcp) |
| ③ | サブエージェント | 独立コンテキストでの並列・役割分担 | [サブエージェント](/themes/04-ai-driven-development/02-claude-code/agents) |
| ④ | Skills（スラッシュコマンド統合） | 定型ワークフローのコマンド化と再利用 | [Skills](/themes/04-ai-driven-development/02-claude-code/skills) / [コマンド](/themes/04-ai-driven-development/02-claude-code/commands) |
| ⑤ | Hooks | 動作前後の自動処理・ガードレール | [Hooks](/themes/04-ai-driven-development/02-claude-code/hooks) |
| ⑥ | 権限制御 | 自律実行の境界設計 | [Claude Code 基礎](/themes/04-ai-driven-development/02-claude-code/basics) |

それぞれを 1 行で要約すると：

- **① コンテキスト設計** — AI が見ている世界の作り方。CLAUDE.md・メモリ・ドキュメント参照で「何を前提に話しているか」を共有する
- **② ツール拡張（MCP）** — AI の手の伸ばし方。Model Context Protocol を介して、ファイルシステムを越えた外部システムにアクセスできるようにする
- **③ サブエージェント** — 役割を分けた小さな AI を並列に走らせ、メインのコンテキストを汚さずにタスクを分担する
- **④ Skills（スラッシュコマンド統合）** — 何度も繰り返す「お決まりの段取り」を再利用可能な部品にし、人間とチームで共有する。旧来の `.claude/commands/*.md` は Skills へ統合され、ユーザーが `/<name>` で起動するだけでなく、Claude が文脈に応じて自動起動することもできる
- **⑤ Hooks** — Claude のツール実行や保存などの **ライフサイクルイベントに紐づけて処理を挟む仕組み**（`PreToolUse` / `PostToolUse` / `SessionStart` など）。コミット前 lint やファイル変更後 format といった自動化と、危険操作の遮断（ガードレール）の両方を担う
- **⑥ 権限制御** — どこまでを自動承認するか、どこから人間に確認を取るかの境界。`default` / `acceptEdits` / `plan` / `bypassPermissions` などの permission mode で表現する（`auto` モードもあるが現時点では研究プレビュー扱い）

> [!IMPORTANT]
> これらは **独立した 6 つではなく、相互に作用する一つの系** です。たとえば「サブエージェントを増やす」ことは「コンテキストの分離（Isolate）」でもあり、「Hooks で format を強制する」ことは「権限制御を弱めても安全にする補強」でもあります。

## 3 層モデル — モデル / ハーネス / プロジェクト

ハーネスエンジニアリングを考えるとき、設計対象を **3 つの層** に分けて捉えると整理しやすくなります。

![モデル層・ハーネス層・プロジェクト層の 3 層モデルと、それぞれの寿命・変えやすさの違い](/content-assets/04-ai-driven-development/01-overview/images/harness-engineering/harness-three-layers.png)

| 層 | 例 | 誰が決める | 寿命 |
| --- | --- | --- | --- |
| モデル層 | Claude Sonnet 4.6 / Opus 4.7（執筆時点） | モデル提供元 | モデル世代と連動 |
| ハーネス層 | Claude Code 本体 + グローバル設定 | 個人 / チーム | 数ヶ月〜数年 |
| プロジェクト層 | `CLAUDE.md` / `.claude/agents/` / `.claude/skills/` / `.claude/settings.json` | リポジトリのオーナー | プロジェクト固有 |

問題が起きたとき、**どの層で解くべきか** を意識すると、解決策の候補が整理できます。

- 「同じ指摘を何度もしている」 → プロジェクト層（CLAUDE.md / Hooks）で対処すべき問題
- 「特定の作業を毎回ゼロから説明している」 → ハーネス層（グローバル Skills / コマンド）に上げるべき
- 「そもそも推論が浅い」 → モデル層の問題（より強いモデルに切り替える）

層を取り違えると、本来プロジェクト固有のルールをグローバルに書いてしまったり、ハーネスで解ける問題をモデル変更で力技解決しようとしたりします。

## 設計原則

ハーネスを組むときの指針として、5 つの原則を挙げます。

1. **ガードレール優先（safety first）**
   自律させる前に Hooks や permission mode で **境界** を作る。`--dangerously-skip-permissions` を使う前に、何が起きても困らない状態にする。
2. **再現性（reproducibility）**
   設定は **リポジトリにコミット** してチームで共有する。`.claude/` 配下に入る agents / skills、および Hooks を含む `.claude/settings.json` は Git 管理対象にする（個人用途や機密値は `.claude/settings.local.json` に分離）。
3. **構成可能性（composability）**
   1 タスク向けの巨大ボットを作るより、**組み合わせで多目的に使える小さな部品** を作る。Unix 哲学と同じ。
4. **観測可能性（observability）**
   AI が何をしたかを後から追える状態を保つ。差分は PR で、コマンドはログで、判断はコメントで残す。
5. **段階的自律（progressive autonomy）**
   いきなり全自動にせず、**信頼度に応じて自動化を引き上げる**。最初は `plan` モードで人間が確認し、安定したら `acceptEdits`、さらに安定すれば `auto` というように段階を踏む。

## よくあるアンチパターン

逆に、ハーネス設計でよく見る失敗例も押さえておきましょう。

- **ガードレール不在の常時バイパス** — `--dangerously-skip-permissions` を癖で付ける。事故が起きるまで気づかない
- **巨大 CLAUDE.md** — すべてのルールを 1 ファイルに詰め込み、コンテキストウィンドウを圧迫する。トークン消費が大きく、肝心の情報が埋もれる
- **サブエージェント乱立** — 役割の似たエージェントを量産し、どれを呼ぶべきか判断が発散する。「役割」より「成果物の種類」で切ると整理しやすい
- **暗黙の自動コミット** — Hook が format → commit → push まで自動化し、レビューが事実上スキップされる。ガードレールのつもりがガードを外している
- **MCP 入れすぎ問題** — 便利そうな MCP サーバーを片っ端から入れ、応答遅延・権限肥大化・ツール選択の迷いを招く。**必要になってから足す** のが基本

> [!WARNING]
> 「自動化を増やすほど良い」ではありません。**増えた自動化が、誰の・どの工程の意思決定を奪っているか** を意識してください。

## 始め方ロードマップ

すべてを一気に揃える必要はありません。**痛みのある定型作業から 1 つずつ** ハーネスに取り込むのが現実的です。推奨順は以下のとおり。

![ハーネス構築の推奨順：CLAUDE.md → スラッシュコマンド → Hooks → サブエージェント → MCP → 権限緩和](/content-assets/04-ai-driven-development/01-overview/images/harness-engineering/harness-roadmap.png)


1. **CLAUDE.md を整える**
   プロジェクト固有のルール・コマンド・命名規約・避けるべき操作を書く。ここが整っていない状態で先に進んでも、AI は前提を共有できない
2. **スラッシュコマンドで定型作業を切り出す**
   「PR レビュー」「リリースノート生成」など、毎回同じ手順でやることをコマンド化する。再利用と共有が一気に進む
3. **Hooks で format / lint / 通知を自動化**
   ファイル保存後の format、コミット前の lint、危険操作の通知を Hook に寄せる。**ガードレールを先に敷く** ことで後段の自動化が安心になる
4. **サブエージェントで並列化・役割分担**
   コードレビュー専門・調査専門・テスト作成専門など、コンテキストを分けたほうが良いタスクをサブエージェント化する
5. **MCP で外部システムにつなぐ（必要になってから）**
   GitHub / Slack / DB など、ファイルシステム外と連携したくなったら MCP サーバーを入れる。**先に入れない**
6. **権限制御を見直し、自律度を段階的に上げる**
   ガードレールが揃ってきたら、permission mode を `plan` → `default` → `acceptEdits` と段階的に引き上げる。さらに自動化を進める場合は `auto`（研究プレビュー）や、隔離環境に限り `bypassPermissions` を使う

> [!TIP]
> 一気にすべてを揃えようとせず、**痛みのある定型作業から 1 つずつ** ハーネスに取り込むのがコツです。順番を守らないと、自動化が事故の温床になります。

## まとめ

- ハーネスエンジニアリング ＝ **AI の動作環境そのものを設計する** 技術
- 主戦場は **「どのモデルを使うか」から「どう設計して使うか」** へ移った
- ハーネスは **コンテキスト / MCP / サブエージェント / Skills / Hooks / 権限** の 6 要素で構成される
- 設計を **モデル / ハーネス / プロジェクト** の 3 層で捉えると、問題の解き先が明確になる
- 原則は **ガードレール優先・再現性・構成可能性・観測可能性・段階的自律**
- 始め方は **CLAUDE.md → コマンド → Hooks → サブエージェント → MCP → 権限緩和** の順
- 各構成要素の具体的な使い方は [Claude Code](/themes/04-ai-driven-development/02-claude-code) モジュールへ
