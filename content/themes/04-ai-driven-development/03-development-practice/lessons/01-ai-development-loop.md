# AI開発の基本ループ

AI 駆動開発では、コードを書くこと自体よりも **「開発の各工程を AI とどう協働して進めるか」** が成果を左右します。本ページでは、開発の基本ループ——**計画 → 実装 → デバッグ → リファクタリング → レビュー**——の全体像と、各ステージで AI をどう使うか、人間に何が残るかを俯瞰します。

> [!NOTE]
> デバッグとリファクタリングは AI 開発の中核なので、具体的なツール機能や実践テクニックは次ページ [AIによるデバッグとリファクタリング](/themes/04-ai-driven-development/03-development-practice/ai-debugging-refactoring) で詳しく扱います。本ページは **ループ全体の地図** です。

## このページで学べること

- AI 開発の **基本ループ**（計画 → 実装 → デバッグ → リファクタリング → レビュー）
- 各ステージで AI を **どう使うか**の概観
- 各ステージを **混ぜない**ことの重要性
- AI に任せきれず **人間に残る判断**

## AI開発の基本ループ

AI と進める開発は、おおむね次のループを回します。各ステージで「AI に任せる部分」と「人間が判断する部分」が分かれます。

| ステージ | 目的 | 代表的な AI 活用 |
| --- | --- | --- |
| 計画 | 何をどう作るか方針を固める | 計画モードで方針を立てさせる |
| 実装 | 方針に沿ってコードを書く | エージェントに実装させ、差分を承認 |
| デバッグ | 不具合の原因を特定し直す | エラーを渡して原因追跡・修正 |
| リファクタリング | 振る舞いを変えず構造を整える | スコープを区切って改善を依頼 |
| レビュー | 品質を確認する | AI コードレビューで指摘を得る |

![AI開発の基本ループ](./images/ai-development-loop-diagram.png)

> [!TIP]
> このループは一方通行ではありません。レビューで問題が見つかればデバッグへ、デバッグ中に構造の悪さに気づけばリファクタリングへ——と行き来します。

## 計画：実装の前に方針を固める

いきなり「作って」と指示すると、AI は的外れな方向に大量のコードを生成しがちです。まず **計画モード**で方針を固め、合意してから実装に入ると手戻りが激減します。

- **Claude Code**：Plan Mode（計画モード）。AI が方針を提示し、承認するまで実際の編集を行わない
- **Cursor**：Plan モード。Agent / Plan / Debug / Ask の 4 モードのうち、計画立案に特化

```text
> /plan
  ユーザープロフィール機能を追加したい。
  既存の認証フローに沿った実装方針を立てて。
  （実装はまだ行わず、方針だけ提示される）
```

## 実装：エージェントに書かせ、差分を承認する

方針が固まったら実装をエージェントに任せます。ポイントは **差分を必ず確認して承認する**ことと、**プロジェクトの文脈を与えておく**ことです。

- `CLAUDE.md` などにプロジェクトのルール・規約を書いておくと、生成コードが既存スタイルに揃う（→ [Claude Code の基本構造](/themes/04-ai-driven-development/02-claude-code/basics)）
- 大きなタスクは一度に頼まず、ステップに分けて依頼すると品質が上がる

## デバッグ・リファクタリング・レビュー

ループの後半——デバッグ・リファクタリング・レビュー——は、AI ツールの機能が特に活きる領域です。概要は次の通りです。

- **デバッグ**：完全なエラー・ログを渡し、AI に原因を追跡・修正させる。Cursor の Debug Mode や Claude Code の調査ループなど、専用機能がある
- **リファクタリング**：スコープを区切って構造改善を依頼する。テストで振る舞いを固定してから行う
- **レビュー**：AI コードレビューで一次チェックする（Cursor Bugbot、GitHub Copilot review、Claude Code `/code-review`）

これらの **具体的なツール機能と実践テクニック**（複数セッションでの相互検証など）は、次ページ [AIによるデバッグとリファクタリング](/themes/04-ai-driven-development/03-development-practice/ai-debugging-refactoring) で詳しく解説します。

> [!IMPORTANT]
> 各ステージは **混ぜないこと**が重要です。特に「振る舞いを変えるデバッグ」と「振る舞いを変えないリファクタリング」を同じ変更に混ぜると、問題が起きたときに原因を切り分けられなくなります。コミットも分けましょう。

## 効率を上げるコツ

- **完全な情報を渡す** — エラーは全文、要件は文脈ごと。曖昧な説明より具体的な入力
- **スコープを区切る** — 「ついでにあれもこれも」を避け、1 回 1 目的に絞る
- **計画を先に** — 実装・修正の前に方針を固め、手戻りを減らす
- **テストで安全網を張る** — AI に大きな変更を任せるほど、テストの価値が上がる

## 試行錯誤と巻き戻しの戦略

AI と進める開発では、試行錯誤が増えます。「この修正で解決するはず → うまくいかない → 別の方針を試す」というサイクルが頻繁に起きるため、**素早く安全に「戻る」ことができる環境**が開発効率を大きく左右します。

### 戻す必要が出る場面

- **セッション内の試行錯誤** — 同じ問題に対して複数の修正案を試したい
- **セッション全体のリセット** — AI が失敗した仮説に引きずられている、別角度から分析したい
- **ファイル・コミット単位の撤回** — 試した修正が不要と判定した、別の方針に切り替えたい

### 3 レベルの巻き戻し

| レベル | ツール・コマンド | 用途 |
| --- | --- | --- |
| **セッション内** | Claude Code `/rewind <N>` | 直近 N ステップをなかったことにし、別の指示を試す |
| **セッション全体** | 新しいセッション開始 | 文脈をリセットし、独立に分析・修正する |
| **コミット・ファイル** | `git checkout` / `git revert` | コミット後の試行錯誤を整理、別方針に切り替える |

> [!TIP]
> **「戻す」前提で試す**ことで、心理的に試行錯誤の敷居が下がります。失敗しても取り返しがつく状態を保つほど、より多くの仮説を短時間で検証でき、結果的に品質が上がることが多いです。詳細な実装方法は、次ページ [AIによるデバッグとリファクタリング](/themes/04-ai-driven-development/03-development-practice/ai-debugging-refactoring) で解説します。

## 人間に残る判断

AI が各ステージを高速化しても、最終的な判断と責任は人間に残ります。

- **方針を決める** — 何を作るか・どう直すかの最終判断
- **差分を確認する** — AI の変更は必ず diff を目視し、意図しない振る舞いの変化を捕まえる
- **採用可否を決める** — 修正案・レビュー指摘・リファクタ案のどれを取り込むか
- **品質責任を持つ** — 動くコードをそのまま本番に流さず、レビューとテストを経る

## まとめ

- AI 開発は **計画 → 実装 → デバッグ → リファクタリング → レビュー** のループで進める
- **計画モード**で方針を固めてから実装すると手戻りが減る
- 各ステージは **混ぜない**（特にデバッグとリファクタリングは別コミット）
- 高速化されても **判断と品質責任は人間**に残る
