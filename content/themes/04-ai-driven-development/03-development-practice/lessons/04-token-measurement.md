# トークン消費の実測と削減の自動化

トークン削減の話題は、ツールやテクニックの紹介から始まりがちです。しかし最適化の鉄則は「**測ってから減らす**」——何がトークンを消費しているかは環境やワークフローによって大きく異なるため、自分の環境を知らないまま対策を打っても、効いているのかどうかすら分かりません。本ページでは、**自分の環境のトークン消費を実測する方法**と、多くの環境で見落とされがちな 2 つの消費源——**同一ファイルの重複読み込み**と**肥大化した設定ファイル**——の見直し、そして**フックによる削減の自動化**を解説します。ここで特定した消費源を外部ツールで削減する方法は、[次のレッスン「AI駆動開発のトークン効率化」](/themes/04-ai-driven-development/03-development-practice/token-efficiency)で扱います。

> [!NOTE]
> 本ページの情報は **2026 年 7 月時点** のものです。また、セッション記録の形式やフックの仕様は Claude Code 固有ですが、「実データから測る」「指示ではなく仕組みで強制する」という考え方自体は、他の AI コーディングエージェントにもそのまま応用できます。コマンド例は macOS / Linux のシェルを前提とします。

## このページで学べること

- `/context`・`/cost` で分かること・**分からないこと**
- セッション記録（transcript）から**自分の環境のツール別トークン消費**を実測する考え方
- 見落とされがちな消費源①——**同一ファイルの重複読み込み**と、`PreToolUse` フックによる抑制
- フック設計の原則——fail open / fail closed の使い分け
- 見落とされがちな消費源②——**設定ファイルの肥大化**と棚卸し（HTML コメントで「トークンゼロのメモ」を残す技法）

## まず組み込みコマンドで — そして、その限界

Claude Code には消費を確認する組み込みコマンドがあります。

| コマンド | 分かること |
| --- | --- |
| `/context` | 現在のコンテキストウィンドウの内訳（システムプロンプト・ツール定義・メッセージなどが何%か） |
| `/cost` | セッションで消費したトークン量とコスト |

日常的にはこの 2 つで十分です。ただし、どちらも**現時点・現セッションのスナップショット**であり、次のような問いには答えられません。

- 先週と比べて消費は増えているのか、減っているのか
- どの**ツール**（ファイル読み込み・コマンド実行・検索…）が消費の主因なのか
- 導入した削減策は、累計でどれだけ効いているのか

こうした「傾向」と「内訳」を知るには、実データにあたる必要があります。

## セッション記録から実測する

Claude Code は、セッションの全記録（transcript）を JSONL 形式で `~/.claude/projects/<プロジェクト>/<セッションID>.jsonl` に保存しています。この中の assistant メッセージには `message.usage` としてトークンの実数が記録されています。

```text
input_tokens                  … 非キャッシュの入力
cache_creation_input_tokens   … キャッシュへの書き込み
cache_read_input_tokens       … キャッシュからの読み込み
output_tokens                 … 出力
```

さらに、`tool_use` ブロック（どのツールを呼んだか）と `tool_result` ブロック（結果の本体）を `tool_use_id` で突き合わせると、「**どのツールが何トークン分の結果をコンテキストに積んだか**」というツール別の内訳まで集計できます。コードを書かなくても、この「どのフィールドを見るか」を知っていれば、jq や小さなスクリプトで自分の環境を測れます。

> [!WARNING]
> transcript の JSONL は Claude Code の**内部形式**で、公式ドキュメントも「バージョン間で変わりうるため、直接パースするスクリプトはリリースのたびに壊れる可能性がある」と明記しています。恒久的な仕組みを作るなら `/export` や Agent SDK の公開インターフェースを検討してください。ここでは「一度測って現状を知る」用途に割り切って使います。

### 何が見えるか

この集計から、「会話に占めるツール実行結果の割合」「ファイル読み込みとコマンド実行のどちらが太いか」「キャッシュ読込・書込の比率」が数字で分かります。コーディングエージェントのセッションでは、**会話内容の大半をツール実行結果が占める**のが一般的ですが、その内訳はワークフローによって大きく異なります——ファイル読み込みが支配的な環境もあれば、テストやビルドの出力が太い環境もあります。そして、[次のレッスン](/themes/04-ai-driven-development/03-development-practice/token-efficiency)で紹介する削減ツールはそれぞれ効く場所が違うため、**どのレバーが自分に効くかは、この内訳で決まります**。だからこそ、対策より先に計測なのです。

> [!WARNING]
> トークン数の代わりに**文字数**を指標にして集計する場合は、**画像・バイナリを必ず除外**してください。transcript には画像が base64 文字列として埋め込まれており、1 枚で数十万文字に膨らむため、除外しないと画像が最大の消費源であるかのように見えます。実際の画像は文字数ではなく**画素数ベース**で課金され（大きな画像は自動ダウンスケールされます）、トークンに換算すると小さいことが多いです（→ [Vision — Claude Docs](https://platform.claude.com/docs/en/vision)）。

## 見落とされがちな消費源① — 同じファイルを何度も読む

エージェントの transcript を観察すると、**同一セッション内で同じファイルを何度も読み直している**ことが珍しくありません。典型的な原因は 3 つに分類できます。

| 原因 | 説明 | 回避できるか |
| --- | --- | --- |
| 編集後の再読（read → edit → read） | 編集の結果を確認するための読み直し。編集が成功したかはツールの結果で分かるため、多くは不要 | ほぼ回避可能 |
| 純粋な重複 | 編集も要約も挟んでいない、特に理由のない読み直し | 回避可能 |
| コンパクション後の再読 | 要約で内容が失われたための再取得 | 正当（ただし部分読みで足りることが多い） |

見落とされがちなのは、「**1 回の読み込みが大きすぎる**」だけでなく「**同じものを何度も読む**」ことが独立した消費源になる、という点です。エージェントは毎ターン会話全体を読み直すため、重複して読み込んだ内容はセッションが続く限り繰り返しコンテキストに積まれ続けます。自分の環境でどの程度起きているかは、前節の方法で transcript から確認できます（Read の対象パスを数えるだけでも傾向は分かります）。これが、[次のレッスン](/themes/04-ai-driven-development/03-development-practice/token-efficiency)で「読む回数を減らす」を独立したレバーとして扱う理由です。

### 対策 — フックで削減を「強制」する

では、どう避けるか。「同じファイルを読み直さないで」と CLAUDE.md に書く方法もありますが、CLAUDE.md の指示は **advisory（助言）**——AI が従わない可能性が常に残ります。確実に止めたいなら、**フック**（hooks）で実行そのものをブロックします。

Claude Code の `PreToolUse` フックは、ツール実行の直前に任意のスクリプトを走らせる仕組みです。スクリプトは stdin から `session_id` / `tool_name` / `tool_input` などを含む JSON を受け取り、**終了コード 2 で終了するとツール実行がブロックされ、stderr の内容がエラーメッセージとして AI に返ります**。つまり「拒否した上で、代わりにどうすべきかを AI に伝える」ことができます。フックの基礎は [hooks のレッスン](/themes/04-ai-driven-development/02-claude-code/hooks)を参照してください。

重複読み対策のフックは、**誤検知のリスクが最も低い条件だけ**で判定するのがコツです。

| 条件 | 判定 |
| --- | --- |
| そのファイルの初回の読み込み | 許可 |
| 前回読んだときから mtime が変わっている（内容が変わった） | 許可 |
| `offset` / `limit` 指定の部分読み | 許可（部分読みは安価） |
| 上記以外の再読 | **拒否** |

実装は「① stdin の JSON から対象ファイルパスを取り出す → ② セッションごとの読み込み記録と照合し、表の条件で判定する → ③ 重複なら stderr にメッセージを出して `exit 2`、それ以外は `exit 0`」という 3 ステップのシェルスクリプトになります。このとき、拒否のメッセージは単に「ダメ」ではなく**逃げ道を示す**のがポイントです。

```text
（ブロック時に AI に返るメッセージの例）
このファイルはこのセッションで読み込み済みで、内容も変わっていません。
再読が必要なら offset / limit で必要な範囲だけ読んでください。
```

「必要なら部分読みで」と案内することで、コンパクション後の正当な再読を完全には塞がず、かつ全体読みではなく安価な部分読みへ誘導できます。なお、この例は `offset` / `limit` 付きの読み込みを無条件で許可しているため、厳密には「完全な強制（hard block）」ではなく、**安価な読み方へ誘導する仕組み**（nudge）です。本当に硬く塞ぎたい場合は許可条件を絞ることになりますが、絞るほど正当な読み込みを誤ってブロックする副作用も増えます。

<details>
<summary>実装例の全文と導入手順（クリックで展開）</summary>

**1. スクリプトを作成** — `~/.claude/hooks/dedupe-read.sh` として保存し、`chmod +x ~/.claude/hooks/dedupe-read.sh` で実行権限を付けます（`jq` のインストールが必要です）。

```bash
#!/bin/bash
# dedupe-read.sh — 同一セッション内の重複 Read をブロックする PreToolUse フック
# 異常時はすべて「許可」に倒す（fail open）
command -v jq >/dev/null 2>&1 || exit 0                   # jq が無ければ素通し

# stdin の JSON から必要な値を 1 回の jq 呼び出しでまとめて取り出す
IFS=$'\t' read -r session file offset limit <<<"$(jq -r \
  '[.session_id // "", .tool_input.file_path // "",
    (.tool_input.offset // "" | tostring), (.tool_input.limit // "" | tostring)] | @tsv')"

if [ -z "$session" ] || [ -z "$file" ]; then exit 0; fi   # 情報が取れない → 許可
if [ -n "$offset" ] || [ -n "$limit" ]; then exit 0; fi   # 部分読み → 許可
[ -f "$file" ] || exit 0                                  # 通常ファイル以外 → 許可

# セッション+ファイルパスをキーに、前回読んだときの mtime を記録・比較する
state_dir="${TMPDIR:-/tmp}/dedupe-read/$session"
mkdir -p "$state_dir" 2>/dev/null || exit 0
key=$(printf '%s' "$file" | { shasum 2>/dev/null || sha1sum 2>/dev/null; } | cut -d' ' -f1)
[ -n "$key" ] || exit 0                                   # ハッシュできない → 許可
# 注: mtime は秒精度。同一秒内の変更は「重複」と誤判定しうる（その場合も部分読みの逃げ道あり）
mtime=$(stat -f %m "$file" 2>/dev/null || stat -c %Y "$file" 2>/dev/null)
[ -n "$mtime" ] || exit 0                                 # mtime が取れない → 許可

prev=$(cat "$state_dir/$key" 2>/dev/null)
echo "$mtime" > "$state_dir/$key"

if [ -n "$prev" ] && [ "$prev" = "$mtime" ]; then         # 初回でも変更後でもない → 拒否
  echo "このファイルはこのセッションで読み込み済みで、内容も変わっていません。再読が必要なら offset / limit で必要な範囲だけ読んでください。" >&2
  exit 2
fi
exit 0
```

**2. フックを登録** — `~/.claude/settings.json`（プロジェクト単位なら `.claude/settings.json`）に、Read ツールの直前にこのスクリプトを実行する設定を追加します。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Read",
        "hooks": [
          { "type": "command", "command": "~/.claude/hooks/dedupe-read.sh" }
        ]
      }
    ]
  }
}
```

**3. 動作確認** — Claude Code を再起動し、同じファイルを 2 回読ませてみます。2 回目の Read がブロックされ、上記のメッセージが AI に返れば成功です。外したいときは settings.json の該当ブロックを削除します（状態ファイルは一時ディレクトリ——`$TMPDIR`、未設定なら `/tmp`——の配下に作られるため、残っても OS が自動的に掃除します）。

判定表の 4 条件（初回の許可・mtime 変化の許可・部分読みの許可・それ以外の拒否）がスクリプトのどこに対応しているかを照らし合わせながら読むと、自分の用途に合わせた改造もしやすくなります。

</details>

### fail open / fail closed — 異常時にどちらへ倒すか

フックを自作すると、必ず設計判断に直面します。**フック自体が壊れたとき（前提コマンドが無い、スクリプトがエラーになる等）、許可に倒すか（fail open）、拒否に倒すか（fail closed）**——答えは一律ではなく、**損害の非対称性**で決めます。

| フックの種類 | 倒す方向 | 理由 |
| --- | --- | --- |
| 品質ゲート（lint・テスト・secrets 検査など） | **fail closed（拒否）** | 素通りすると「守られているつもりで無防備」になり、成功と区別がつかない |
| 読み込み抑制（今回の重複読みブロック） | **fail open（許可）** | 壊れたときに全ファイル読み込みが止まると、作業そのものが完全に停止する |

前節の実装例の随所に `|| exit 0`（異常時は許可）が置かれていたのは、まさにこの判断の現れです。「安全側に倒す」という言葉の意味が、ケースによって正反対になる——ここがフック設計のいちばんの学びどころです。

## 見落とされがちな消費源② — 設定ファイルの肥大化

もう 1 つ、多くの環境で見直す価値があるのが、**毎セッション自動で読み込まれる設定類**（CLAUDE.md と `@import` されるファイル群）です。これはセッションのたびに必ず支払う**固定費**であり、フレームワークや設定集を導入すると `@import` が積み上がっていきます。放置すると、固定費が数千〜数万トークン規模に膨らむこともあります。CLAUDE.md 本体を 500 行以下に保つ話は[メモリとコンテキスト管理](/themes/04-ai-driven-development/02-claude-code/memory)で扱いましたが、`@import` 先まで含めた**合計の投入量**で棚卸しすることが重要です。

### 対策 — 死荷重の種類ごとに「外す・移す」

溜まりやすい「死荷重」は典型的に 3 種類あり、置き場所が違うため対策もそれぞれ異なります。共通の原則は「**いきなり削除しない**」——外し方を誤ると、必要になったときに戻せなくなるからです。

| 死荷重 | 置き場所 | 対策 |
| --- | --- | --- |
| 使わなくなったフレームワークやモードの説明 | CLAUDE.md からの `@import` | **`@import` の行を外す**（参照先のファイルは削除しない）。復元手順は後述の HTML コメントで残す |
| 無効化済み・削除済みの MCP サーバーの解説ドキュメント | CLAUDE.md からの `@import`（MCP 本体の設定とは**別管理**） | MCP サーバー本体を外す操作（`claude mcp remove` や `.mcp.json` の編集）では、解説ドキュメント側は消えない。**サーバーを外すときに、対応する `@import` も同時に外す** |
| 特定のプロジェクトでしか使わないルール | グローバルの `~/.claude/CLAUDE.md` 本文 | 削除ではなく、**そのプロジェクトの `CLAUDE.md` へ移動**する。プロジェクト配下の CLAUDE.md はそのプロジェクトでのみ読み込まれるため、他の作業の固定費にならない |

1 行目・2 行目の「`@import` を外す」を安全に行うための道具が、次の HTML コメントです。

### HTML コメント — トークンゼロでメモを残す技法

棚卸しで一番困るのは「消してしまうと、後で戻せなくなる」ことです。ここで、Claude Code の公式仕様が 2 つ役立ちます。

1. **`@import` の解析は、コードスパン・フェンスコードブロック内をスキップする** — バッククォートで囲めば import されない。ただし**テキスト自体はコンテキストに載る**（トークンは消費する）
2. **CLAUDE.md 内のブロックレベル HTML コメント（`<!-- ... -->`）は、コンテキスト投入前に除去される** — つまり**トークンを 1 つも消費しない**（コードブロック内のコメントは除去されない点に注意）

この 2 つ目が決定打です。無効化した設定の復元手順を HTML コメントとして CLAUDE.md に書き残しておけば、**人間には見えて、AI のコンテキストには一切載らない**メモになります。

```markdown
# Global Instructions

@my-rules.md

<!--
Framework X — YYYY-MM-DD に常時ロードを停止
理由: 常時ロードの @import 群が数万トークン規模に達していた
戻すには: 下の1行を @import に戻す
FrameworkX/MODES.md ほか
-->
```

あわせて、無効化するときは**ファイルを削除せず `@import` の行を外すだけ**にしておくと、フレームワークの再インストールと衝突せず、1 行の変更で元に戻せます。

## まとめ

- **測ってから減らす。** `/context`・`/cost` は現時点のスナップショット。傾向とツール別内訳はセッション記録（transcript）から実測できる——ただし内部形式なので「現状把握」用途に割り切る（文字数で集計するなら画像・バイナリは除外する）
- 見落とされがちな消費源は「**同一ファイルの重複読み**」と「**肥大化した設定ファイル**」。どちらも多くの環境で起きうるので、自分の環境で確認する価値がある
- 確実に止めたい削減ロジックは、CLAUDE.md の指示（advisory）ではなく **`PreToolUse` フックで強制**する。異常時に倒す方向は損害の非対称性で決める——品質ゲートは fail closed、読み込み抑制は fail open
- 設定の棚卸しは、死荷重の種類ごとに「**外す・移す**」で対処し、いきなり削除しない。復元手順は **HTML コメント**でトークンゼロで書き残せる
- ここまでが「測る・無駄を止める」。**外部ツールで積極的に減らす**方法は[次のレッスン](/themes/04-ai-driven-development/03-development-practice/token-efficiency)へ
