# AI駆動開発のトークン効率化

AI 駆動開発では、AI とのやり取りはすべて**トークン**という単位で数えられ、課金され、そしてコンテキストウィンドウを消費していきます。[コンテキストエンジニアリング](/themes/04-ai-driven-development/01-overview/context-engineering)では「限られたコンテキストをどう管理するか」という考え方を、[メモリとコンテキスト管理](/themes/04-ai-driven-development/02-claude-code/memory)では `/compact` などの組み込み機能を学びました。本ページはその続きとして、**トークンの消費そのものを減らす**——つまり「増えたものを後から整理する」のではなく「**そもそも増やさない**」——ための実践を扱います。主役は、Serena・rtk・Headroom という 3 つの外部ツールです。

> [!NOTE]
> 本ページのツール情報（導入手順・コマンド・公称の削減率など）は **2026 年 7 月時点** のものです。この分野は変化が非常に速く、手順や仕様は今後変更される可能性があります。導入の際は、ページ末尾の「参考リソース」にまとめた各公式ドキュメント・リポジトリで最新情報を確認してください。
>
> また、本ページでは Claude Code を例に解説しますが、トークン消費の構造は Cursor でも Codex CLI でも Gemini CLI でも同じです。紹介する 3 ツールも、いずれも複数の AI コーディングエージェントに対応しています。コマンド例は macOS / Linux のシェルを前提とします。

## このページで学べること

- なぜトークンを節約するのか——**コストだけの話ではない**理由
- トークンが「**どこで**」消えているのか、可視化する方法（`/context`・`/cost`）
- 削減が効く **4 つのレバー**——読む量を減らす / 読む回数を減らす / 出力を圧縮する / 届く前に圧縮する
- 「トークン削減率」と「コスト削減率」が一致しない理由——**キャッシュの経済**
- **Serena** — ファイルを「全部読まない」ためのセマンティックコード検索
- **rtk** — コマンド出力を AI に渡す前に圧縮する CLI プロキシ
- **Headroom** — LLM に届く直前でコンテキスト全体を圧縮するエンジン
- 3 ツールの使い分けと、組み合わせの考え方

## なぜトークンを節約するのか — コストだけの話ではない

「トークン節約」と聞くと、お金をケチる話に聞こえるかもしれません。しかし AI 駆動開発でトークン効率が重要な理由は、実は 3 つあります。

| 理由 | 何が起きるか |
| --- | --- |
| **コスト** | API は入出力トークン数に応じた従量課金。サブスクリプションプランでも利用上限（レート制限）はトークン量で決まる |
| **速度** | 入力が大きいほど応答は遅くなる。無駄なトークンは毎ターンの待ち時間として跳ね返る |
| **精度** | コンテキストウィンドウが埋まるほど、重要な情報が薄まり応答品質が落ちる。上限に達すればオートコンパクト（要約）が走り、情報が失われる |

特に見落とされがちなのが 3 つ目です。**トークン効率はコンテキスト効率**でもあります。同じ 1 つの作業を 5 万トークンで終えるのと 20 万トークンかけて終えるのとでは、後者は途中で要約（情報の損失）を挟む可能性が高く、精度面でも不利になります。節約は「我慢」ではなく、**速く・安く・賢く**動かすための技術です。

### キャッシュの経済 — 「トークン削減率」は「コスト削減率」ではない

コストについては、先に 1 つ補正しておくべき事実があります。**入力トークンの課金は一律ではありません**。Claude をはじめ主要な LLM API には**プロンプトキャッシュ**の仕組みがあり、Claude の場合、キャッシュから読み込まれた入力は基本価格の **0.1 倍**で課金されます。エージェントは毎ターン会話の先頭から読み直すため、長く続くセッションでは**入力の大部分がこの 0.1 倍のキャッシュ読込**になります。つまり「素のトークン数が半分になればコストも半分」という直感は成り立ちません。

一方で、逆方向の事実もあります。**毎ターン、会話全体を読み直す**ということは、コンテキストに一度入った内容は、セッションが続く限り**何十回・何百回と繰り返し課金され続ける**ということです。ターン数の多いエージェント作業では、ユニークな会話内容に対して課金対象の入力が数百倍に膨らむことも珍しくありません。つまり、**内容そのものを減らす施策は複利で効く**——本ページのツール群が「そもそも増やさない」ことにこだわるのはこのためです。

> [!NOTE]
> キャッシュには「先頭からの並び（プレフィックス）が変わると無効化される」性質もあります。闇雲にコンテキストを圧縮・書き換えするとキャッシュが壊れ、かえって高くつくことがあります（後述の Headroom が CacheAligner という仕組みを持つのはこの問題への対策です）。自分の環境のキャッシュ比率や増幅の程度を実測する方法は、[前のレッスン「トークン消費の実測と削減の自動化」](/themes/04-ai-driven-development/03-development-practice/token-measurement)で解説しています。

## トークンはどこで消えているのか

減らす前に、まず「どこで消えているか」を知る必要があります。エージェントのコンテキストに入るものを分解すると、おおよそ次の通りです。

| 消費源 | 内容 | 特徴 |
| --- | --- | --- |
| システムプロンプト・ツール定義 | エージェント本体の指示と、使えるツールの説明 | 毎ターン固定で乗る |
| CLAUDE.md・設定類 | プロジェクトのルール、メモリ | 自分で減らせる（[500 行以下が目安](/themes/04-ai-driven-development/02-claude-code/memory)） |
| 会話履歴 | これまでのやり取り | `/compact`・`/clear` で整理できる |
| **ツール実行の結果** | **読み込んだファイルの中身、コマンドの出力** | **多くのセッションで最大の消費源** |

注目すべきは最後の行です。長めのセッションでトークンを最も食うのは、あなたが打ったプロンプトでも会話履歴でもなく、**AI が作業のために読み込んだファイルとコマンド出力**であることがほとんどです。具体例を挙げると——

- 目的の関数は 20 行なのに、それを探すために 1,500 行のファイルを丸ごと読む
- テストは 1 件失敗しただけなのに、成功した 200 件分のログまで全部コンテキストに入る
- `tree` を実行したら `node_modules/` まで出力されて数千行になる

こうした「作業には必要だが、**中身のほとんどはノイズ**」というデータが、毎ターン積み上がっていきます。

### まず可視化する

自分のセッションで何が圧迫しているかは、Claude Code なら組み込みコマンドで確認できます。

| コマンド | 分かること |
| --- | --- |
| `/context` | 現在のコンテキストウィンドウの内訳（システムプロンプト・ツール定義・メッセージなどが何%か） |
| `/cost` | セッションで消費したトークン量とコスト |

なお、`/context` が見せてくれるのは**現時点のスナップショット**です。「先週より増えたのか」「どのツールの出力が消費源なのか」といった傾向・内訳まで踏み込んだ実測は、[前のレッスン](/themes/04-ai-driven-development/03-development-practice/token-measurement)で扱っています。

> [!TIP]
> 最適化の鉄則は「**測ってから減らす**」です。`/context` で一番太い消費源を特定してから、それに効くツールを選んでください。CLAUDE.md が肥大しているなら分割（→ [メモリとコンテキスト管理](/themes/04-ai-driven-development/02-claude-code/memory)）、ツール定義が多いなら MCP の整理（→ [MCP](/themes/04-ai-driven-development/02-claude-code/mcp)）、そして**ファイル読み込みとコマンド出力が太いなら、本ページの外部ツールの出番**です。

## 削減の4つのレバー

トークン消費を減らすアプローチは、データの流れのどこに介入するかで 4 つに整理できます。

```text
 あなたの指示
    │
    ▼
 ①【読む量を減らす】── ファイル全体ではなく必要な部分だけを読む   … Serena
 ②【読む回数を減らす】── 同じファイルの重複読みを防ぐ           … 自作フック
    │
    ▼
 ③【出力を圧縮する】── コマンド出力をノイズ除去してから渡す      … rtk
    │
    ▼
 ④【届く前に圧縮する】── LLM への送信直前にコンテキスト全体を圧縮 … Headroom
    │
    ▼
 LLM（モデル本体）
```

| レバー | 発想 | 代表ツール・手法 |
| --- | --- | --- |
| ① 読む量を減らす | ファイル全体ではなく、必要なシンボル（関数・クラス）だけ読む | **Serena** |
| ② 読む回数を減らす | 同じファイルを同一セッション内で何度も読み直さない | **自作フック**（→ [前のレッスン](/themes/04-ai-driven-development/03-development-practice/token-measurement)） |
| ③ 出力を圧縮する | `git status` やテスト出力を、要点だけに絞ってから AI に見せる | **rtk** |
| ④ 届く前に圧縮する | ツール出力・ログ・JSON を、LLM に送る直前に自動圧縮する | **Headroom** |

② は意外に思えるかもしれませんが、エージェントは同一セッション内で**同じファイルを何度も読み直す**ことが珍しくありません（編集後の確認・要約後の再取得・特に理由のない重複——分類は[前のレッスン](/themes/04-ai-driven-development/03-development-practice/token-measurement)を参照）。「1 回の読み込みが大きすぎる」だけでなく「同じものを何度も読む」ことが、独立した消費源になりえます。② には既製ツールがなく `PreToolUse` フックの自作で対処するため、詳細は前のレッスンに譲り、本ページでは既製の外部ツールがある **①・③・④** を扱います。

すでに学んだ組み込み機能——`/compact` による要約、[サブエージェント](/themes/04-ai-driven-development/02-claude-code/agents)によるコンテキスト分離、[MCP のツールサーチ](/themes/04-ai-driven-development/02-claude-code/mcp)——は、いずれも「**増えたコンテキストを後から整理・隔離する**」働きです。それに対して本ページの 3 ツールは「**最初から増やさない**」側に効きます。両者は競合せず、組み合わせて使うものです。

## Serena — ファイルを「全部読まない」ためのMCPサーバー

**Serena** は、Oraios AI が開発するオープンソース（MIT ライセンス）の MCP サーバーです。「コーディングエージェントのための IDE」を標榜し、**LSP（Language Server Protocol）**——VS Code などの IDE がコード補完や定義ジャンプに使っているのと同じ仕組み——を通じて、AI にコードを**シンボル（関数・クラス・メソッド）単位**で読み書きさせます。Python / TypeScript / Java / Go / Rust など 40 以上の言語に対応しています。

### なぜトークン節約になるのか

外部ツールなしの AI は、コードをテキストとして扱います。「`calculateTotal` 関数を修正して」と頼むと、典型的にはこう動きます。

```text
❌ テキスト検索ベースの動き
   grep "calculateTotal" → 5 ファイルがヒット
   → 1 つずつファイルを丸ごと読む（1,500 行 × 5 ファイル）
   → ようやく目的の 20 行を特定
   ＝ 数千〜数万トークンを消費
```

Serena を入れると、同じ作業がシンボル単位になります。

```text
✅ シンボル検索ベースの動き
   find_symbol("calculateTotal") → 定義位置と本体 20 行だけを取得
   find_referencing_symbols     → 参照箇所だけをピンポイントで取得
   ＝ 必要な数百トークンで完結
```

主要なツールは次の通りです。

| ツール | 役割 |
| --- | --- |
| `get_symbols_overview` | ファイルの中身を読まずに、構造（シンボル一覧）だけを俯瞰する |
| `find_symbol` | 名前でシンボルを検索し、本体だけを取得する |
| `find_referencing_symbols` | そのシンボルを参照している箇所を横断検索する |
| `replace_symbol_body` / `insert_after_symbol` | シンボル単位でコードを書き換える・追記する |
| `rename_symbol` / `safe_delete_symbol` | LSP の力でプロジェクト全体に及ぶリネーム・安全な削除を 1 回の呼び出しで行う |

公式 README は「典型的な代替手段よりはるかにトークン効率的（much more token-efficient）」と説明しています。「◯% 削減」という公式の数値は公表されていませんが、「ファイル全読みの連鎖」が「シンボル単位の取得」に置き換わるという仕組み上、**大規模なコードベースほど効果が大きくなります**。

### 導入方法

Serena は Python 製で、`uv` でインストールしてから Claude Code に接続します。

```bash
# 1. Serena 本体をインストール
uv tool install --python 3.13 serena-agent
serena init

# 2. Claude Code に自動セットアップ
serena setup claude-code
```

手動で接続したい場合は `claude mcp add` を使います。

```bash
# プロジェクト単位で接続する場合
claude mcp add serena -- serena start-mcp-server --context claude-code --project "$(pwd)"
```

> [!WARNING]
> Serena の公式 README は「**MCP マーケットプレイス経由でインストールしないこと**」と明記しています。また、以前広く紹介されていた `uvx --from git+... serena-mcp-server --context ide-assistant` という手順は**旧形式**です（エントリポイントは `serena start-mcp-server` に改名され、`ide-assistant` コンテキストは非推奨）。古い記事の手順をそのままコピーせず、公式ドキュメントの現行手順に従ってください。

### 注意点

- Claude Code は組み込みの検索・読み込みツールを優先しがちで、Serena のツールが使われないことがあります。公式は対策として、システムプロンプトの上書き（`serena prompts print-cc-system-prompt-override`）や hooks の設定を案内しています。
- LSP の起動やインデックス作成にはそれなりの初期コストがあります。数ファイルの小さなプロジェクトでは、恩恵よりセットアップの手間が勝つこともあります。

## rtk — コマンド出力をAIに渡す前に圧縮するCLIプロキシ

**Serena が「読むファイル」に効くなら、rtk は「実行するコマンド」に効きます。** **rtk（Rust Token Killer）** は、シェルと LLM の間に立つオープンソース（Apache-2.0 ライセンス）の CLI プロキシです。依存関係のない単一の Rust バイナリで、`git` / `cargo` / `pytest` / `docker` など 100 以上のコマンドの出力を、AI に渡す前にフィルタ・圧縮します。

### 仕組み — 「AI に必要な情報」だけを残す

人間向けに整形されたコマンド出力には、AI の判断に不要な装飾やノイズが大量に含まれています。rtk は 4 つの戦略でそれを削ぎ落とします。

| 戦略 | 内容 |
| --- | --- |
| Smart Filtering | 装飾・進捗表示などのノイズを除去する |
| Grouping | 類似した項目をまとめて集約する |
| Truncation | 関連するコンテキストだけを残して切り詰める |
| Deduplication | 重複する行を「N 回」の形に畳み込む |

たとえば `rtk git status` は、変更がなければ `ok main` という一言だけを返します。テスト実行なら、成功した数百件のログは捨てて**失敗したものだけ**を残します。公称の削減率は「一般的な開発コマンドで **60〜90%**」。README には、30 分のセッションで `ls`/`tree` 系 80% 減、テスト出力 90% 減、セッション合計で約 118,000 → 約 23,900 トークン（約 80% 減）という例が示されています。

ただし、この公称値は**コマンド単体**での削減率です。セッション全体への寄与は「コマンド出力がコンテキスト全体に占める割合」が上限になります。多くのコーディングセッションでは最大の消費源はコマンド出力ではなく**ファイル読み込み**なので、コマンド出力を 60〜90% 削っても、セッション全体で見れば 1〜2 割程度の寄与にとどまることもあります。公称値と矛盾しているのではなく、分母が違うだけです。自分の環境でコマンド出力が占める割合は[前のレッスン](/themes/04-ai-driven-development/03-development-practice/token-measurement)の方法で確認できます。「導入すればセッション全体が 60〜90% 軽くなる」わけではない、という期待値で導入しましょう。

### 導入方法

```bash
# インストール（公式スクリプト）
curl -fsSL https://raw.githubusercontent.com/rtk-ai/rtk/refs/heads/master/install.sh | sh

# または cargo で（必ず --git 指定で。理由は下の警告参照）
cargo install --git https://github.com/rtk-ai/rtk
```

> [!TIP]
> `curl | sh` 形式は手軽ですが、外部スクリプトをそのまま実行することになります。[AI駆動開発のセキュリティとsecrets管理](/themes/04-ai-driven-development/03-development-practice/ai-security-secrets)で学んだ姿勢の延長として、気になる場合は一度ダウンロードして中身を確認してから実行すると安全です。

Claude Code との統合は `rtk init` で行います。これは Claude Code の **hooks**（PreToolUse）を設定し、AI が実行する Bash コマンドを透過的に `rtk <cmd>` へ書き換える仕組みです。AI 側は何も意識せず、出力だけが圧縮されます。

```bash
rtk init -g          # グローバルに hook を設定（対話式）
rtk init --show      # 設定内容の確認
# 設定後は Claude Code の再起動が必要
```

日常的に使う確認コマンドも揃っています。

| コマンド | 用途 |
| --- | --- |
| `rtk gain` | 累計でどれだけトークンを節約できたかの統計を表示 |
| `rtk gain --history` | コマンドごとの節約履歴を表示 |
| `rtk discover` | 過去の履歴を分析し、まだ圧縮できていない機会を提案 |
| `rtk proxy <cmd>` | フィルタなしの素通し実行（圧縮で情報が落ちていないか疑ったときのデバッグ用） |

> [!WARNING]
> **crates.io にある同名の `rtk` は別プロジェクト**（Rust Type Kit — Rust コードから型を生成するツール）です。`cargo install rtk` と打つとそちらが入ってしまいます。必ず公式スクリプトか `cargo install --git https://github.com/rtk-ai/rtk` を使ってください。入っているのがどちらか分からなくなったら、`rtk gain` が統計を表示すれば Token Killer の方です。

### 注意点

- 圧縮は「情報を捨てる」ことでもあります。テスト失敗の原因調査などで「圧縮前の生の出力が見たい」と感じたら、`rtk proxy <cmd>` で素通しできることを覚えておいてください。
- hooks による透過的な書き換えは強力な反面、「AI が実行したコマンドと実際に走ったコマンドが異なる」状態です。挙動が不可解なときは `rtk init --show` で設定を確認しましょう。

## Headroom — LLMに届く直前でコンテキストを圧縮するエンジン

3 つ目の **Headroom**（headroomlabs-ai/headroom）は、最も下流——**LLM への送信直前**——に介入するオープンソース（Apache-2.0 ライセンス）のコンテキスト圧縮エンジンです。ツール出力・ログ・ファイル・RAG チャンクといったコンテキストを対象に、「回答品質は同等のまま」トークンを削減することを目標としています。公称値は、コーディングエージェントで約 20% 削減、JSON データでは 60〜95% 削減です。

### 仕組み — 内容の種類ごとに専用の圧縮器を使う

Headroom の特徴は、データの種類に応じて圧縮方法を切り替えることです。

| コンポーネント | 対象と方法 |
| --- | --- |
| SmartCrusher | JSON 構造（配列・ネスト）を構造を保ったまま圧縮する |
| CodeCompressor | tree-sitter による **AST（構文木）ベース**でコードを圧縮する |
| テキスト圧縮モデル | エージェントの実行トレースで学習した小型モデルで一般テキストを要約する |
| CacheAligner | 圧縮してもプロンプトキャッシュのプレフィックスを壊さないよう整合を取る |
| CCR（可逆圧縮） | 圧縮前のオリジナルをローカルに保存し、**必要になったら AI が取り出せる** |

特に最後の 2 つが設計として重要です。**CacheAligner** は「圧縮したせいでプロンプトキャッシュが効かなくなり、かえってコストが増える」という本末転倒を防ぎます。**CCR** は「圧縮 = 情報を捨てる」のリスクへの答えで、削った情報も失われず、AI が後から参照できます。

### 導入方法

```bash
# インストール
pip install "headroom-ai[all]"
# または
uv tool install --python 3.13 "headroom-ai[all]"
```

Claude Code と組み合わせる最も簡単な方法は `wrap` です。ローカルプロキシが起動し、Claude Code の全通信に自動で圧縮が適用されます。

```bash
headroom wrap claude
```

このほか、Python ライブラリとして自作エージェントに組み込む方法（`compress(messages)`）や、プロキシ単体起動（`headroom proxy --port 8787`）、MCP サーバーとしての利用にも対応しています。

### 導入前に知っておくべき3つの但し書き

1. **公式自身が「見送ってよい人」を明記しています。** README の "When to use · When to skip" には「**単一プロバイダの組み込みコンパクションだけで足りていて、エージェント横断のメモリも不要なら見送ってよい**」という趣旨の記載があります。Claude Code は自前のコンパクション（`/compact`・オートコンパクト）を持つため、この見送り条件に該当する人は少なくありません。
2. **削減率の表示は、そのままでは推定値です。** `export HEADROOM_OUTPUT_HOLDOUT=0.1` を設定すると会話の約 10% が未圧縮の対照群（ホールドアウト）になり、対照群のデータが溜まるとダッシュボードの Output Tokens Saved 表示が `estimated`（推定）から `measured`（実測）に変わります。導入するかどうかの判断は、**必ずホールドアウト付きの実測**で行いましょう。
3. **`headroom wrap claude` は、Serena を code-memory MCP として自動登録します**（実体は `uvx` 経由のオンデマンド実行）。本ページの手順ですでに Serena を導入済みの場合や不要な場合は、`--code-memory none` を付けると登録を無効化できます。

> [!NOTE]
> 「Headroom」の名前では、もう 1 つ**商用のデスクトップアプリ**（Headroom Desktop / extraheadroom.com）が存在します。こちらは macOS のメニューバーに常駐し、内部で headroom（プロンプト最適化）と rtk（CLI 出力圧縮）の**両方**を使って Claude Code / Codex のトラフィックを最適化する製品です（公称約 50% 削減、有料プラン $3/月〜）。「設定なしで全部やってほしい」人向けの製品化版という位置づけで、本ページで解説した OSS エンジンとは別物として区別してください。

## 3ツールの使い分けと組み合わせ

3 つのツールは介入するレイヤーが違うため、**排他ではなく積み上げ**られます。改めて整理します。

| | Serena | rtk | Headroom |
| --- | --- | --- | --- |
| 効く場所 | ファイル読み込み・コード検索 | コマンド実行の出力 | LLM への送信全体 |
| 形態 | MCP サーバー | CLI プロキシ（hooks 統合） | 圧縮エンジン（wrap / proxy / ライブラリ） |
| 導入の手軽さ | 中（uv + MCP 設定） | 高（インストール + `rtk init -g`） | 中（pip + `wrap`） |
| 特に向く状況 | 大規模コードベースの探索・リファクタリング | テスト・ビルド・git 操作が多いセッション | JSON・ログなど大きな構造化データを扱うとき |
| 効果の確認 | — | `rtk gain` | 削減率のログ |

導入の順序に迷ったら、次の指針をおすすめします。

1. **まず測る** — `/context`・`/cost`、必要なら[前のレッスン](/themes/04-ai-driven-development/03-development-practice/token-measurement)の実測手法で、自分のセッションの太い消費源を特定する
2. **一番効くレバーから 1 つ入れる** — コード探索が太いなら Serena、コマンド出力が太いなら rtk
3. **効果を測ってから次を足す** — `rtk gain` や `/cost` の変化で削減を確認し、必要なら組み合わせる

> [!IMPORTANT]
> 「ツールを足すこと」自体にもコストがあります。MCP サーバーを増やせばツール定義がコンテキストに乗り、ハーネスは複雑になります——1 サーバーで数十個のツールを公開する MCP サーバーも珍しくありません（→ [ハーネスエンジニアリング](/themes/04-ai-driven-development/01-overview/harness-engineering)の「MCP 入れすぎ問題」）。全部入れるのが正解ではなく、**測って、効くものだけを入れる**のが正解です。

## 人間に残る判断

ツールは圧縮を自動化してくれますが、次の判断は人間に残ります。

- **どこを削るかを決める** — 可視化（`/context`・`/cost`）して最大の消費源を特定するのは自分の仕事
- **圧縮と情報損失のバランスを取る** — 削りすぎて AI の判断材料が失われていないか。挙動が不可解なら `rtk proxy` での素通しや CCR での復元など、「生データに戻る手段」を確認する
- **節約を目的化しない** — 最優先は成果物の品質。トークン効率化は「同じ品質をより少ないコストで」実現する手段であって、品質を削ってまで行うものではない

## まとめ

- トークン効率化はコスト削減だけでなく、**速度と精度**（コンテキスト圧迫の回避）のための技術
- 入力課金は一律ではない——長いセッションでは大部分が 0.1 倍のキャッシュ読込。ただし内容は毎ターン読み直されて繰り返し課金されるため、**内容を減らす施策は複利で効く**
- 最大の消費源は多くの場合**ツール出力**（ファイル読み込み・コマンド実行結果）。まず `/context`・`/cost` で測る
- 削減のレバーは 4 つ——**読む量を減らす（Serena）・読む回数を減らす（自作フック）・出力を圧縮する（rtk）・届く前に圧縮する（Headroom）**
- 組み込み機能（`/compact`・サブエージェント・ツールサーチ）が「増えたら整理する」側なのに対し、外部ツールは「**そもそも増やさない**」側。両輪で使う
- 全部入れるのではなく、**測って、効くものだけを入れる**
