# AIによるデバッグとリファクタリング

[前ページ](/themes/04-ai-driven-development/03-development-practice/ai-development-loop) で見た開発ループのうち、**デバッグ**と**リファクタリング**は AI ツールの機能が最も活きる領域です。本ページでは、主要ツールの専用機能と、**複数のセッションや別の AI ツールを使った相互検証**など、AI ならではの実践テクニックを掘り下げます。

> [!NOTE]
> デバッグやリファクタリングの **原理原則**（原因特定の考え方、コードの臭い、安全な進め方など、ツールに依存しない知識）は、別テーマ [ソフトウェアエンジニアリング基礎](/themes/05-software-engineering) にまとめています。本ページは「AI ツールでどう進めるか」に集中します。

## このページで学べること

- AI デバッグの基本（エラーを渡す → 直す）と、主要ツールの **デバッグ専用機能**
- **複数セッション・別ツールでの相互検証**で、単一セッションでは見つからないバグを発見する
- AI リファクタリングの進め方（スコープを区切る・一括リネーム）
- **AI コードレビュー**の活用（Bugbot / Copilot / Claude Code）
- デバッグ・リファクタリングで **人間に残る判断**

## AIデバッグの基本

AI 時代のデバッグの基本は驚くほどシンプルです——**完全なエラー文・ログを渡す → AI が原因と修正案を提示 → 検証する**。多くの不具合（構文エラー、null 参照、型エラー）はこれで即座に解決します。

```bash
# エラーログをそのまま渡す
cat error.log | claude -p "このエラーの原因と、調査すべき箇所を挙げて"

# 失敗したテストの出力を渡す
npm test 2>&1 | claude -p "失敗しているテストの原因を特定して修正方針を立てて"
```

> [!IMPORTANT]
> 「発生箇所（where）」と「原因（why）」は別物です。スタックトレースは **落ちた場所** を教えてくれますが、原因はその上流にあることが少なくありません。簡単なバグでは両者が一致するので AI が即解決しますが、ログに原因が出ないバグ（想定と違う出力・競合状態・状態管理・間欠的な失敗）では切り分けが必要です。原理は [デバッグの基礎](/themes/05-software-engineering/01-debugging) を参照してください。

## 主要ツールのデバッグ機能

各ツールには、デバッグを支援する専用機能があります。

### Claude Code

エラーやログを渡すと、**コードベース全体を横断して原因を追跡**します。特徴的なのは、`Edit` と `Bash` を使って **「再現 → 修正 → 再テスト（reproduce → patch → retest）」のループを実際に回せる**点です。推測で終わらず、コマンドを実行して仮説を確かめながら直します。

- **計画モード**で「診断」と「修正」を分離し、方針に合意してから直す
- **サブエージェント**（root-cause 系）に独立した文脈で原因調査を任せる

### Cursor Debug Mode

Cursor の **Debug Mode** は、ランタイム情報と人間による検証を中心に据えたデバッグ専用のエージェントループです。AI が **複数の仮説を立て、コードに自動でログを計装**し、実際の変数の状態・実行経路を見て原因を特定します。再現と修正の確認は人間が担う設計です。

### GitHub Copilot

**デバッガエージェント**が、失敗しているテストを起点に **エラーを読む → 原因をコードベース横断で追跡 → 修正を当てる → 再実行して確認**まで自動で進めます。実行中のプログラムの状態を見て、例外の原因を説明させることもできます。

| ツール | デバッグ機能の特徴 |
| --- | --- |
| Claude Code | コードベース横断の追跡＋reproduce→patch→retest ループ、計画モード、サブエージェント |
| Cursor Debug Mode | 仮説生成＋自動ログ計装＋ランタイム観察 |
| GitHub Copilot | 失敗テスト起点のデバッガエージェント、実行時状態の説明 |
| OpenAI Codex | テスト失敗を反復的に修正するエージェント（専用の「デバッグモード」は持たないが、自律的に修正と再テストを繰り返す） |

## 複数セッション・別ツールでの相互検証

ここが AI デバッグで見落とされがちな、しかし強力なテクニックです。**1 つのセッション・1 つのツールだけに頼ると、見つけられないバグがあります。**

### なぜ単一セッションでは不十分か

- **確証バイアス** — AI は自分が立てた仮説や、自分が書いた修正に引きずられます。同じ文脈で「これで合ってる？」と聞いても、肯定的に答えがちです
- **文脈の汚れ** — 長いセッションは誤った前提を引きずり、間違った方向に固執することがあります
- **モデルの盲点** — 1 つのモデルが見落とすパターンは、そのセッション内では埋まりません

### 相互検証のやり方

独立した視点をぶつけることで、これらの弱点を補えます。

| 手法 | やること | 効果 |
| --- | --- | --- |
| 新セッションで再調査 | 文脈をリセットし、前の結論を伝えず独立に原因を分析させる | 先入観・文脈の汚れを排除 |
| 別ツール / 別モデルで検証 | Claude Code の修正を Cursor Bugbot や別モデルにレビューさせる | 異なる盲点を持つAI同士で穴を埋める |
| 敵対的検証 | 別セッションに「この修正の誤り・見落としを指摘して」と反証を求める | 確証バイアスを打ち消す |
| サブエージェントで並列調査 | 独立した文脈で複数のエージェントに原因を調べさせ、結論を突き合わせる | 多角的な原因候補を得る |

```text
（別セッション・別ツールでの敵対的検証の例）
> 別のセッションで以下の修正を独立にレビューして。
  「正しい」と仮定せず、誤り・見落とし・別の原因の可能性を
  積極的に指摘して。
```

> [!TIP]
> 特に効果的なのは **「片方で直し、もう片方で疑う」** 役割分担です。たとえば Claude Code で修正し、Cursor Bugbot や別モデルのレビューに「この修正は本当に正しいか」を独立に検証させます。一方が見落としたバグを、もう一方が捕まえます。

> [!CAUTION]
> 相互検証はコスト（時間・トークン）がかかります。すべてのバグに使う必要はなく、**再現しにくいバグ・原因不明のバグ・重要箇所（セキュリティ・決済・データ整合性）の修正**に絞るのが現実的です。また、異なるモデルでも同じ訓練データ由来の盲点を共有することがあり、「複数が同意したから正しい」とは限りません。最終確認は人間が行います。

## AIリファクタリングの進め方

リファクタリング（振る舞いを変えず構造を改善する作業）で AI を使う最大のコツは、**スコープを明示的に区切る**ことです。AI は頼めばいくらでも「改善」しますが、放任すると差分が巨大化し、振る舞いまで変えてしまいます。

```text
> このファイルをリファクタリングして。今回は「重複の排除」と
  「長い関数の分割」だけに絞って。振る舞いを変える変更はしないで。
```

- **一括リネーム**：Claude Code はシンボルの参照箇所を追えるため、変数・関数のリネームを参照ごと安全に行える
- **簡素化**：Claude Code の `/simplify` で冗長な箇所の整理を依頼できる
- **横断的な変更**：Cursor や GitHub Copilot の agent mode は、命名規約の統一や重複ロジックの共通化など、ファイル横断の機械的変換が得意
- **大規模リファクタ・マイグレーション**：OpenAI Codex は、フレームワーク移行やプロジェクト全体の構造変更といった大規模なリファクタを、テスト失敗を修正しながら end-to-end で進めるのが得意

> [!CAUTION]
> リファクタリングは **テストで振る舞いを固定してから** 行うのが鉄則です。AI に大きな書き換えを任せるほど、テストの安全網が重要になります。安全な進め方の原則は [安全なリファクタリングの進め方](/themes/05-software-engineering/02-refactoring/safe-refactoring) を参照してください。

## AIコードレビューの活用

実装・修正・リファクタしたコードは、AI コードレビューで機械的に一次チェックできます。主要ツールはいずれも **プルリクエスト（PR）に対する自動レビュー**を提供しています。これは前述の「相互検証」を仕組み化したものとも言えます。

| ツール | 機能 | 特徴 |
| --- | --- | --- |
| Cursor Bugbot | PR を自動レビューし、論理バグ・セキュリティ・エッジケースを指摘 | **Autofix**（修正を自動生成）、Rules（独自基準）に対応 |
| GitHub Copilot | PR にインラインコメントで指摘、CLI の `/review` | GitHub プラットフォームと密に統合 |
| Claude Code | `/code-review`、`/simplify`、クラウド多エージェントの `ultrareview` | ローカルの差分・ブランチをその場でレビュー |
| OpenAI Codex | CLI の `/review`、PR への `@codex review`／全 PR 自動レビュー | 指摘箇所を `@codex fix it` で修正、`AGENTS.md` のレビュー基準に従う |

> [!NOTE]
> AI レビューの指摘は「気づきのきっかけ」としては優秀ですが、**すべてを鵜呑みにしない**こと。好みの問題や、このプロジェクトでは不要な指摘（false positive）も混じります。採用判断は必ず人間が行います。

## 人間に残る判断

AI がデバッグ・リファクタリングを高速化しても、次の判断は人間に残ります。

- **再現のトリガーを引く** — バグを再現する操作・条件は人間が用意する（AI が検証するため）
- **修正が本物か確認する** — 症状を隠しただけ（エラーの握りつぶし等）でないかを見極める
- **差分を確認する** — AI の変更は必ず diff を目視し、意図しない振る舞いの変化を捕まえる
- **検証の落としどころを決める** — どこまで相互検証するか、どの指摘を採用するか
- **品質責任を持つ** — 動くコードをそのまま本番に流さず、レビューとテストを経る

## まとめ

- デバッグの基本は **エラーを渡す → 直す**。Claude Code の reproduce→patch→retest、Cursor Debug Mode、Copilot デバッガエージェントが調査を自動化する
- **複数セッション・別ツールでの相互検証**で、単一セッションでは見つからないバグを発見できる（新セッションで再調査・別モデルで検証・敵対的検証）
- 相互検証はコストがかかるので、**難しい/重要なバグ**に絞る。「複数が同意＝正しい」とは限らない
- リファクタリングは **スコープを区切り**、テストで振る舞いを固定してから行う
- レビューは **Bugbot / Copilot review / Claude `/code-review` / Codex `@codex review`** で一次チェックし、採用は人間が判断
