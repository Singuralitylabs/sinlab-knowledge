# Routines とスケジュール実行

Claude Code には、プロンプトを自動で繰り返し実行する仕組みが **3 つ** 用意されています。クラウドで動く **Routines**、自分のマシンで動く **デスクトップスケジュールタスク**、セッション内で完結する **`/loop`** です。名前も画面も似ているため混同しやすいのですが、実行場所・永続性・ローカルファイルへのアクセス可否が明確に異なり、用途で選び分けます。

このページでは 3 方式の違いを整理したうえで、それぞれの設定方法と実務上の注意点を解説します。

> [!NOTE]
> 本記事の内容は **2026 年 8 月時点** のものです。Routines は **リサーチプレビュー** 段階であり、挙動・上限・API の仕様は変更される可能性があります。実際に利用する際は[公式ドキュメント](https://code.claude.com/docs/en/routines)を併せて確認してください。

## このページで学べること

- 3 つのスケジュール実行方式の違いと選び分けの基準
- Hooks との役割の違い（何をきっかけに動くのか）
- Cloud Routines の 3 種類のトリガー（スケジュール / API / GitHub イベント）
- デスクトップスケジュールタスクの権限設定と取りこぼし時の挙動
- `/loop` の固定間隔・動的間隔・`loop.md` によるカスタマイズ
- cron 式・ジッター・7 日自動失効といった時間まわりの仕様
- 自律実行させるうえでの安全上の注意点

## 3 つの方式の違い

### なぜ 3 つあるのか

「定期的に Claude を動かす」と一口に言っても、要件は次のように分かれます。

- **PC の電源が落ちていても確実に動いてほしい** → クラウドで動かすしかない
- **ローカルのファイルやツールを触ってほしい** → 自分のマシンで動かすしかない
- **今開いているセッションで、ビルドの完了を数分おきに見張ってほしい** → セッション内で十分

この 3 つの要件がそのまま 3 方式に対応しています。

### 比較表

| | Cloud Routines | デスクトップスケジュールタスク | `/loop` |
| --- | --- | --- | --- |
| 実行場所 | クラウド（既定は Anthropic 管理） | 自分のマシン | 自分のマシン |
| マシンの起動が必要 | 不要 | 必要 | 必要 |
| セッションを開いておく必要 | 不要 | 不要 | **必要** |
| 再起動をまたいだ永続 | ✓ | ✓ | `--resume` で復元（未失効のもの） |
| ローカルファイルへのアクセス | 不可（毎回クローン） | 可 | 可 |
| MCP / コネクタ | タスクごとに設定 | 設定ファイル + コネクタ | セッションから継承 |
| 実行中の権限プロンプト | **なし**（完全自律） | タスクごとに設定可 | セッションから継承 |
| 最小間隔 | 1 時間 | 1 分 | 1 分 |
| トリガー種別 | スケジュール / API / GitHub | スケジュールのみ | スケジュールのみ |

> [!TIP]
> 迷ったときの基準はシンプルです。**マシンに依存せず確実に回したい定型業務は Cloud**、**ローカルのファイルやツールが必要なら Desktop**、**作業中の一時的なポーリングなら `/loop`** を選びます。

### Hooks との違い

同じ「自動化」カテゴリでも、[Hooks](/themes/04-ai-driven-development/02-claude-code/hooks) とスケジュール実行は役割が異なります。

| 観点 | Hooks | スケジュール実行（Routines / `/loop`） |
| --- | --- | --- |
| 位置づけ | エージェントループの **内側** に割り込む | セッションを **外から起動** する |
| きっかけ | ツール実行前後などのライフサイクルイベント | 時刻・API 呼び出し・GitHub イベント |
| 実行されるもの | シェルコマンド等のハンドラ | Claude のセッションそのもの |
| 判断主体 | `matcher` による機械的な判定 | LLM がプロンプトを解釈して作業 |

Hooks は「Claude が動いている最中に、必ず実行したい処理を差し込む」仕組みです。対してスケジュール実行は「Claude のセッション自体を、決まったきっかけで開始する」仕組みです。両者は競合せず、Routines のセッション内でも Hooks は通常どおり発火します。

## Cloud Routines

### Routines とは

Routine は、**プロンプト・対象リポジトリ・コネクタを 1 セットにして保存した Claude Code の設定** です。一度作っておけば、トリガーが条件を満たすたびにクラウド上でセッションが自動起動します。ローカルマシンの状態に依存しないため、ノート PC を閉じていても動き続けます。

利用には **Pro / Max / Team / Enterprise プラン** かつ **Claude Code on the web が有効** であることが必要です。作成と管理は [claude.ai/code/routines](https://claude.ai/code/routines) か、CLI の `/schedule` コマンド（別名 `/routines`）から行います。

```text
/schedule daily PR review at 9am
```

CLI から実行すると、Claude がスケジュール・対象リポジトリ・プロンプトについて質問しながら Routine を保存してくれます。Web・デスクトップ・CLI のどこから作っても同じクラウドアカウントに保存されるため、作成した Routine は他のどの画面からも見えます。

> [!IMPORTANT]
> Routine は **個人の claude.ai アカウントに紐づきます**。チームメンバーとは共有されません。また、Routine が GitHub やコネクタ経由で行った操作はすべて **あなたの名義** になります。コミットや PR はあなたの GitHub ユーザーとして作成され、Slack や Linear への書き込みもあなたの連携アカウントで実行されます。

### 3 種類のトリガー

Routines の最大の特徴は、スケジュール以外のトリガーが使えることです。1 つの Routine に複数のトリガーを付けられるため、「毎晩定期実行しつつ、新しい PR が来たときにも走る」といった構成が可能です。

| トリガー | 起動条件 | 主な用途 |
| --- | --- | --- |
| スケジュール | 毎時 / 毎日 / 平日 / 毎週、または将来の特定時刻に 1 回 | 定期レビュー、バックログ整理、ドキュメントの陳腐化チェック |
| API | 専用エンドポイントへの HTTP POST | 監視ツールのアラート連携、デプロイ後の検証 |
| GitHub | リポジトリのイベント（PR・リリース） | PR の自動レビュー、リリース時の連動処理 |

#### スケジュールトリガー

フォームからは毎時・毎日・平日・毎週のプリセットを選びます。時刻はローカルタイムゾーンで入力し、自動で変換されるため、クラウドの所在地に関わらず指定した時刻に実行されます。

「2 時間おき」「毎月 1 日」のようなプリセットにない間隔は、CLI の `/schedule update` で cron 式を直接指定します。**最小間隔は 1 時間** で、それより短い式は拒否されます。

> [!NOTE]
> 実行はスケジュール時刻から数分ずれることがあります（API トラフィックを分散させるためのジッター）。ずれ幅は Routine ごとに一定です。

単発実行も設定できます。「ロールアウト完了後にクリーンアップ PR を出す」「2 週間後にフィーチャーフラグを削除する」といった用途に向いており、実行後は自動的に無効化されます。**単発実行は日次の実行回数上限にカウントされません**。

```text
/schedule in 2 weeks, open a cleanup PR that removes the feature flag
```

#### API トリガー

API トリガーを追加すると、その Routine 専用の HTTP エンドポイントとベアラートークンが発行されます。監視システム・デプロイパイプライン・社内ツールなど、認証付きの HTTP リクエストを送れる場所から Claude Code を起動できます。

```bash
# 監視ツールのアラートを Routine に渡して調査させる
curl -X POST https://api.anthropic.com/v1/claude_code/routines/trig_XXXXXXXX/fire \
  -H "Authorization: Bearer sk-ant-oat01-xxxxx" \
  -H "anthropic-beta: experimental-cc-routine-2026-04-01" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"text": "Sentry alert SEN-4521 fired in prod. Stack trace attached."}'
```

成功するとセッション ID と URL が返り、ブラウザで実行の様子をリアルタイムに追えます。

```text
{
  "type": "routine_fire",
  "claude_code_session_id": "session_01HJKLMNOPQRSTUVWXYZ",
  "claude_code_session_url": "https://claude.ai/code/session_01HJKLMNOPQRSTUVWXYZ"
}
```

> [!WARNING]
> リクエストボディの `text` は、そのまま指示として扱われるわけではありません。`<routine-fire-payload>` ブロックで包まれ、**信頼できないデータ** として Claude に渡されます。Routine 側のプロンプトが「`routine-fire-payload` ブロックに記載されたアラートを調査してください」のように明示的に参照しない限り、`text` は単なる文脈情報として無視されます。これはトークンが漏れた場合に、任意の指示を注入されることを防ぐための設計です。

トークンは **生成時に一度しか表示されません**。アラートツールのシークレットストアなど安全な場所に保管してください。ローテーションや無効化は同じ画面から行えます。

#### GitHub イベントトリガー

リポジトリのイベントに反応して、新しいセッションを自動起動します。イベントごとに独立したセッションが作られるため、PR が 2 回更新されれば 2 つのセッションが立ち上がります。

| イベント | 発火タイミング |
| --- | --- |
| Pull request | PR が open / close / assign / label / synchronize などされたとき |
| Release | リリースが作成 / 公開 / 編集 / 削除されたとき |

フィルタで対象を絞り込めます。指定した条件は **すべて満たされた場合のみ** 起動します。

| フィルタ項目 | 対象 |
| --- | --- |
| Author | PR 作成者の GitHub ユーザー名 |
| Title / Body | PR のタイトル / 本文 |
| Base branch / Head branch | マージ先 / マージ元のブランチ |
| Labels | 付与されたラベル |
| Is draft / Is merged | ドラフトかどうか / マージ済みかどうか |

演算子は equals・contains・starts with・is one of・is not one of・matches regex から選びます。

> [!CAUTION]
> `matches regex` は **フィールド全体** に対するマッチです。タイトルに `hotfix` を含むものを拾いたい場合は `.*hotfix.*` と書く必要があります。`hotfix` だけを指定すると、タイトルがちょうど `hotfix` の PR にしかマッチしません。部分一致でよければ `contains` を使うほうが安全です。

利用には対象リポジトリへの **Claude GitHub App のインストール** が必要です。CLI の `/web-setup` はクローン用のアクセス権を付与するだけで、App のインストールと Webhook の配信は有効になりません。

### 実行環境とネットワーク

Routine はクラウド環境上で実行され、環境がネットワークアクセス・環境変数・セットアップスクリプトを制御します。

既定の **Default** 環境は **Trusted** ネットワークアクセスで、パッケージレジストリやクラウドプロバイダ API など許可リストに載ったドメインのみ通します。許可外のホストへのリクエストは `403` と `x-deny-reason: host_not_allowed` で失敗します。自社サービスに直接アクセスする必要がある場合は、環境設定で **Custom** を選んでドメインを追加してください。

> [!NOTE]
> コネクタの通信は Anthropic のサーバ経由でルーティングされるため、**許可リストへの追加は不要** です。Slack や Linear を使う Routine のためにドメインを開ける必要はありません。

リポジトリは実行のたびに既定ブランチからクローンされます。Claude は変更を `claude/` プレフィックスのブランチにプッシュします。プロンプトで別のブランチを指定した場合、保護ブランチ・他人の PR が出ているブランチ・他人のコミットを含むブランチへのプッシュは拒否されます。

### 自律実行であることの注意

Routines は **承認プロンプトのない完全自律セッション** として動作します。権限モードの選択肢はなく、実行中に確認を求められることもありません。

> [!CAUTION]
> Routine に含めたコネクタについて、Claude は **書き込みを含むすべてのツールを許可なく使えます**。作成フォームでは連携済みのコネクタが既定ですべて含まれるため、**その Routine に不要なコネクタは必ず外してください**。同様に、環境変数は同じ環境を使う全員から見えるため、認証情報を置く際は注意が必要です。

もう 1 つの落とし穴が実行結果の見方です。

> [!IMPORTANT]
> 実行一覧のステータスが緑になっていても、それは **セッションがインフラ的なエラーなく起動・終了した** ことを示すだけで、**プロンプトのタスクが成功したことは意味しません**。ネットワークのブロック、コネクタのツール不足、タスクレベルの失敗はいずれもステータスには現れません。実際に何が起きたかは実行を開いてトランスクリプトを読む必要があります。

### 実行回数の上限

Routines は通常のセッションと同じようにサブスクリプションの使用量を消費します。それに加えて、**アカウントごとに 1 日あたりの実行開始回数の上限** があります。上限に達すると、使用クレジットを有効にしている場合は従量課金で継続でき、そうでなければウィンドウがリセットされるまで拒否されます。

Team / Enterprise では、オーナーが管理画面のトグルで組織全体の Routines を無効化できます。無効化すると既存の Routine も停止します。

## デスクトップスケジュールタスク

ローカルのファイルやツールにアクセスする必要がある場合は、こちらを使います。デスクトップアプリのサイドバーで **Routines** → **New routine** → **Local** を選ぶと作成できます（**Cloud** を選ぶと前述の Cloud Routines になります）。

### 設定項目

| 項目 | 内容 |
| --- | --- |
| Name | タスクの識別子。小文字ケバブケースに変換され、ディスク上のフォルダ名になる |
| Description | 一覧に表示される短い説明 |
| Instructions | 実行内容。通常のプロンプトと同じ書き方でよい。権限モードとモデルの選択、作業フォルダとワークツリー分離の指定もここで行う |
| Schedule | 実行頻度（Manual / Hourly / Daily / Weekdays / Weekly） |

作業フォルダの指定は必須です。**Manual** を選ぶとスケジュール実行はされず、手動で **Run now** したときだけ動きます（プロンプトを保存しておく用途に便利です）。プリセットにない間隔は、任意のセッションで「テストを 6 時間おきに実行するタスクを作って」のように自然言語で頼めば設定できます。

> [!TIP]
> 既定ではタスクは **作業ディレクトリの現在の状態**（未コミットの変更を含む）に対して実行されます。作成時にワークツリーのトグルを有効にすると、実行ごとに独立した Git ワークツリーが割り当てられ、進行中の作業と干渉しなくなります。

### 実行条件と取りこぼし

タスクが動くのは **デスクトップアプリが起動していて、かつコンピュータが起きている間だけ** です。スリープ中にスケジュール時刻を過ぎると、その回はスキップされます。設定の「Keep computer awake」でアイドルスリープは防げますが、ラップトップの蓋を閉じればスリープします。

取りこぼしには救済措置があります。アプリ起動時やスリープ復帰時に、過去 7 日以内の未実行がないか確認され、**直近 1 回分だけ** が追いかけ実行されます。6 日間実行できなかった日次タスクも、復帰時に走るのは 1 回だけです。

> [!WARNING]
> 追いかけ実行があるため、**朝 9 時に設定したタスクが夜 11 時に動く** ことがあります。時刻が意味を持つプロンプトには、ガードを書き込んでおいてください。たとえば「本日のコミットのみをレビューしてください。17 時を過ぎている場合はレビューをスキップし、未処理分の要約だけを報告してください」のように書きます。

### 権限

タスクごとに権限モードを設定でき、`~/.claude/settings.json` の allow ルールも適用されます。Manual モードで権限のないツールを使おうとすると、**承認されるまで実行が止まります**。セッションはサイドバーに残るので後から答えることもできますが、無人実行を前提にするなら避けたい挙動です。

停止を防ぐには、タスク作成後に一度 **Run now** を実行し、出てくる権限プロンプトで「always allow」を選んでおきます。以降の実行では同じツールが自動承認されます。承認内容はタスクの詳細ページから確認・取り消しできます。

### タスクの実体

プロンプトはディスク上に保存されており、直接編集できます。

```bash
# タスクのプロンプトを編集する
$EDITOR ~/.claude/scheduled-tasks/<task-name>/SKILL.md
```

このファイルは `name` と `description` を YAML フロントマターに持ち、本文がプロンプトになります。変更は次回実行から反映されます。スケジュール・フォルダ・モデル・有効状態はこのファイルには含まれないため、編集フォームか Claude への依頼で変更します。

## `/loop`（セッション内スケジュール）

`/loop` は、**開いているセッションの中でプロンプトを繰り返す** バンドルスキルです。デプロイの完了待ち、PR の見張り、長いビルドの確認など、その場限りのポーリングに向いています。

### 3 つの使い方

渡す引数によって挙動が変わります。

| 渡すもの | 例 | 挙動 |
| --- | --- | --- |
| 間隔とプロンプト | `/loop 5m check the deploy` | 固定間隔で実行 |
| プロンプトのみ | `/loop check the deploy` | Claude が毎回間隔を判断して実行 |
| 間隔のみ / 何もなし | `/loop` | 組み込みのメンテナンスプロンプト（または `loop.md`）を実行 |

**固定間隔** は `s` / `m` / `h` / `d` の単位で指定します。秒は分に切り上げられ、`7m` や `90m` のように cron のステップに綺麗に収まらない値は近い値に丸められます（丸めた結果は Claude が教えてくれます）。

**間隔を省略** すると、Claude が各回の結果を見て 1 分〜1 時間の範囲で次の待ち時間を決めます。ビルドが終わりかけていれば短く、動きがなければ長く待つ、という調整が入ります。選んだ間隔とその理由は毎回出力されます。

```text
/loop check whether CI passed and address any review comments
```

スキルを渡すこともできます（`/loop 20m /review-pr 1234`）。ただし `/model` のような組み込みコマンドや、`disable-model-invocation: true` が指定されたスキルは実行されず、単なるテキストとして渡ります。

> [!TIP]
> 動的な間隔を頼むと、Claude は `/loop` の代わりに **Monitor ツール** を使うことがあります。バックグラウンドでスクリプトを走らせて出力行をそのまま流す仕組みで、ポーリング自体が不要になるぶんトークン効率と反応速度で有利です。

### `loop.md` で既定のプロンプトを差し替える

引数なしの `/loop` が使うプロンプトは、`loop.md` を置くことで差し替えられます。

| パス | スコープ |
| --- | --- |
| `.claude/loop.md` | プロジェクト単位（両方ある場合はこちらが優先） |
| `~/.claude/loop.md` | ユーザー単位 |

中身は構造の決まっていない普通の Markdown です。`/loop` にそのまま打ち込む文章を書く感覚で構いません。

```markdown
`release/next` の PR を確認してください。CI が失敗していれば失敗したジョブの
ログを取得し、原因を診断して最小限の修正をプッシュしてください。新しい
レビューコメントが来ていれば、それぞれに対応してスレッドを解決してください。
すべて問題なく静かであれば、その旨を 1 行で報告してください。
```

編集は次の周回から反映されるため、ループを走らせたまま指示を調整できます。25,000 バイトを超える内容は切り詰められるので簡潔に保ってください。

### 停止と自動失効

待機中に `Esc` を押すとループが止まります。動的間隔モードでは、タスクが完了したと判断すれば Claude 自身がループを終了することもあります。

> [!IMPORTANT]
> 定期タスクは **作成から 7 日で自動的に失効** します。最後に 1 回だけ発火してから自身を削除する仕様で、忘れられたループが動き続けるのを防ぐためのものです。7 日を超えて回したい場合は、失効前に作り直すか、Cloud Routines かデスクトップスケジュールタスクを使ってください。

### 時間まわりの仕様

`/loop` の裏側では cron ベースのスケジューラが動いています。実務で引っかかりやすい仕様を挙げます。

- **タイムゾーン**: すべてローカルタイムゾーンで解釈されます。`0 9 * * *` は UTC の 9 時ではなく、Claude Code を動かしている場所の 9 時です。
- **発火のタイミング**: スケジューラは毎秒チェックしますが、プロンプトが発火するのは **ターンとターンの間** です。Claude が応答の途中であれば、そのターンが終わるまで待ちます。
- **ジッター**: 定期タスクは最大 30 分（1 時間未満の間隔なら間隔の半分まで）遅れて発火します。ずれ幅はタスク ID から決まるため毎回同じです。正確な時刻が必要なら `0 9 * * *` ではなく `3 9 * * *` のように `:00` や `:30` を避けます。
- **取りこぼしの補填なし**: 長い処理の最中に時刻を過ぎた場合、アイドルに戻った時点で 1 回だけ発火します。逃した回数分は実行されません。
- **セッションの寿命**: 新しい会話を始めるとタスクは消えます。`claude --resume` / `--continue` で再開すると、未失効の定期タスクと未到来の単発タスクが復元されます。

一回限りのリマインダは自然言語で頼めます。

```text
in 45 minutes, check whether the integration tests passed
```

タスクの一覧や取り消しも同様です。内部的には `CronCreate` / `CronList` / `CronDelete` の 3 ツールが使われ、1 セッションで最大 50 件まで登録できます。

```text
what scheduled tasks do I have?
```

> [!NOTE]
> スケジューラを完全に止めたい場合は、環境変数 `CLAUDE_CODE_DISABLE_CRON=1` を設定します。cron ツールと `/loop` が使えなくなり、登録済みのタスクも発火しなくなります。

## 使い分けの実例

| やりたいこと | 適した方式 | 理由 |
| --- | --- | --- |
| 平日朝に前日マージ分のリリースノート案を作る | Cloud Routines | PC の状態に依存せず確実に回したい |
| 新しい PR にチーム独自のレビュー観点を適用する | Cloud Routines（GitHub トリガー） | イベント駆動はクラウドのみ |
| 監視アラートを受けて調査と修正 PR を起票する | Cloud Routines（API トリガー） | 外部システムから起動する必要がある |
| ローカルの作業フォルダを毎晩整理する | デスクトップスケジュールタスク | ローカルファイルにアクセスする必要がある |
| ローカルの開発 DB に対してテストを定期実行する | デスクトップスケジュールタスク | ローカルのツールと環境が必要 |
| 走らせたビルドの完了を待って結果を知りたい | `/loop` | 一時的なポーリングで十分 |
| PR の CI とレビューコメントを作業中だけ見張る | `/loop`（動的間隔） | セッションを開いている間だけでよい |

## 注意点と落とし穴

無人で動く自動化は、便利さと引き換えに「気付かないうちに何かが起きる」リスクを持ちます。

> [!CAUTION]
> **不可逆な操作を自動化の対象にしない。** 送金・メッセージ送信・本番環境への反映・データ削除といった取り返しのつかない操作は、承認を挟めない Cloud Routines には向きません。まずは調査・要約・ドラフト作成といった読み取り中心のタスクから始め、実行履歴を定期的にレビューしてください。

> [!WARNING]
> **プロンプトは自己完結させる。** Routine は自律実行されるため、会話の流れで補足することができません。「何をするか」と「何をもって成功とするか」を、そのプロンプトだけで判断できるように明記する必要があります。

> [!WARNING]
> **コネクタと環境変数のスコープを絞る。** Routine に含めたコネクタのツールは、書き込みを含めて許可なく使われます。不要なものは外してください。

| 症状・制限 | 回避策 |
| --- | --- |
| `/loop` のタスクが 7 日で消えた | 仕様。恒久的に回すなら Cloud Routines かデスクトップスケジュールタスクへ移行する |
| デスクトップタスクが動いていない | アプリが起動しているか、コンピュータがスリープしていないかを確認する。実行履歴でスキップ理由を確認できる |
| デスクトップタスクが権限待ちで止まる | 一度 **Run now** して「always allow」を選び、必要なツールを事前に承認しておく |
| 実行ステータスは緑なのに成果物がない | ステータスは起動と終了しか見ていない。トランスクリプトを開いて実際の挙動を確認する |
| Routine から自社 API に到達できない | クラウド環境のネットワークアクセスを Custom にしてドメインを追加する |
| `/schedule` が「Unknown command」になる | claude.ai アカウントでのログインが必要。API キー認証やクラウドプロバイダ経由のログインでは使えない |

## まとめ

- Claude Code のスケジュール実行には **Cloud Routines / デスクトップスケジュールタスク / `/loop`** の 3 方式がある
- 選択の基準は **マシンに依存せず回したいか**・**ローカルファイルが必要か**・**セッションを開いたままでよいか** の 3 点
- Cloud Routines だけが **スケジュール以外のトリガー**（API・GitHub イベント）を持ち、複数のトリガーを 1 つの Routine に併用できる
- Cloud Routines は **承認プロンプトのない完全自律実行**。コネクタと環境変数のスコープを絞り、不可逆な操作は任せない
- デスクトップタスクは **アプリ起動中かつ非スリープ時のみ** 動作し、取りこぼしは直近 1 回だけ追いかけ実行される
- `/loop` は **セッション内限定** で最小 1 分間隔。7 日で自動失効するため恒久的な自動化には向かない
- [Hooks](/themes/04-ai-driven-development/02-claude-code/hooks) が「ループの内側に割り込む」仕組みであるのに対し、スケジュール実行は「ループを外から起動する」仕組み
