# Routines とスケジュール実行

普段の Claude Code は、こちらが何かを打ち込んで初めて動きます。ここで扱うのは、その逆です。**あらかじめ指示を保存しておき、決まった時刻や決まった出来事をきっかけに、Claude のほうから勝手に動き出す** 仕組みです。

たとえばこんなことができます。

- 毎朝 9 時に、前日マージされた変更をまとめてリリースノートの下書きを作っておく
- 新しいプルリクエストが作られた瞬間に、チーム独自の観点でレビューコメントを付けておく
- 監視ツールがエラーを検知したら、その場で原因を調べて修正案のプルリクエストまで出しておく

Claude Code には、この「自動で動かす」仕組みが **3 つ** 用意されています。クラウドで動く **Cloud Routines**、自分のパソコンで動く **デスクトップスケジュールタスク**、そして開いている会話の中だけで動く **`/loop`** です。名前も画面も似ていて混同しやすいのですが、**どこで動くか**・**電源を切っても生き残るか**・**手元のファイルを触れるか** が明確に違います。

このページでは、まず 3 方式の違いを整理し、そのうえでそれぞれの設定手順と実務上の注意点を解説します。

> [!NOTE]
> 本記事の内容は **2026 年 8 月時点** のものです。Routines は **研究プレビュー**（正式版の前の試験公開）段階であり、挙動・上限・API の仕様は変更される可能性があります。実際に利用する際は[公式ドキュメント](https://code.claude.com/docs/en/routines)を併せて確認してください。

## このページで学べること

- 3 つのスケジュール実行方式の違いと選び分けの基準
- Cloud Routines を**画面のボタンから作って実行する**手順
- Cloud Routines の 3 種類のきっかけ（スケジュール / API / GitHub イベント）とその設定方法
- GitHub のイベントと連携する仕組み（何がどう繋がっているのか）
- デスクトップスケジュールタスクの権限設定と取りこぼし時の挙動
- `/loop` が実際に役に立つ場面と、引数なし `/loop` の中身
- 時刻の指定にまつわるクセ（実行時刻のずれ・7 日で消える仕様）
- 人が見ていない場所で動かすうえでの安全上の注意点

## まず押さえておきたい 3 つの言葉

以降の説明で繰り返し出てくる言葉です。ここだけ先に押さえておけば、あとは読み進められます。

| 言葉 | 意味 |
| --- | --- |
| **プロンプト** | Claude への指示文。「何をしてほしいか」を書いた文章そのもの |
| **セッション** | Claude との会話 1 回分 |
| **トリガー**（きっかけ） | 自動実行を開始させる合図。「毎朝 9 時になったら」「PR が作られたら」といった条件 |

つまり自動実行とは、**「トリガー（きっかけ）が来たら、保存しておいたプロンプトを実行する」** という仕組みです。Cloud Routines とデスクトップスケジュールタスクは、トリガーのたびに**新しいセッション**を 1 つ立ち上げます。対して `/loop` だけは新しいセッションを作らず、**今開いている会話にプロンプトを追加投入する**という違いがあります（この違いが `/loop` の使いどころに直結します。詳しくは後述）。

## 3 つの方式の違い

### なぜ 3 つあるのか

「定期的に Claude を動かす」と一口に言っても、要件は次のように分かれます。

- **パソコンの電源が落ちていても確実に動いてほしい** → クラウドで動かすしかない
- **手元のフォルダにあるファイルやツールを触ってほしい** → 自分のパソコンで動かすしかない
- **今開いている画面で、ビルドの完了を数分おきに見張ってほしい** → 会話の中で完結すれば十分

この 3 つの要件がそのまま 3 方式に対応しています。

### 比較表

| | Cloud Routines | デスクトップスケジュールタスク | `/loop` |
| --- | --- | --- | --- |
| 実行場所 | クラウド（既定は Anthropic 管理） | 自分のパソコン | 自分のパソコン |
| パソコンの起動が必要 | 不要 | 必要 | 必要 |
| Claude Code を開いておく必要 | 不要 | 不要 | **必要** |
| 再起動をまたいで残るか | 残る | 残る | `--resume` で復元（7 日以内のもの） |
| 手元のファイルを触れるか | 不可（毎回リポジトリを取得し直す） | 可 | 可 |
| 外部サービス連携（MCP / コネクタ） | Routine ごとに設定 | 設定ファイル + コネクタ | 会話から引き継ぐ |
| 実行中の権限確認 | **なし**（完全自律） | タスクごとに設定可 | 会話から引き継ぐ |
| 最短の実行間隔 | 1 時間 | 1 分 | 1 分 |
| きっかけの種類 | スケジュール / API / GitHub | スケジュールのみ | スケジュールのみ |

> [!TIP]
> 迷ったときの基準はシンプルです。**パソコンの状態に左右されず確実に回したい定型業務は Cloud**、**手元のファイルやツールが必要なら Desktop**、**作業中の一時的な見張りなら `/loop`** を選びます。

## Cloud Routines

### Routines とは

Routine は、**プロンプト・対象リポジトリ・外部サービス連携を 1 セットにして保存した Claude Code の設定** です。一度作っておけば、きっかけの条件を満たすたびにクラウド上でセッションが自動的に始まります。手元のパソコンの状態に依存しないため、ノート PC を閉じていても動き続けます。

利用には **Pro / Max / Team / Enterprise プラン** かつ **Claude Code on the web が有効** であることが必要です。作成と管理は次の 3 か所から行え、**どこで作っても同じアカウントに保存される** ため、作った Routine は他のどの画面からも見えます。

| 作成場所 | 特徴 |
| --- | --- |
| デスクトップアプリ | 画面のフォームで作る。すべてのきっかけを設定できる |
| Web（[claude.ai/code/routines](https://claude.ai/code/routines)） | デスクトップアプリと同じフォーム |
| CLI の `/schedule` コマンド | 会話しながら作る。手軽だが一部の設定は Web が必要 |

> [!IMPORTANT]
> Routine は **個人の claude.ai アカウントに紐づきます**。チームメンバーとは共有されません。また、Routine が GitHub や外部サービス経由で行った操作はすべて **あなたの名義** になります。コミットや PR はあなたの GitHub ユーザーとして作成され、Slack や Linear への書き込みもあなたの連携アカウントで実行されます。

### 画面から作る（デスクトップアプリ / Web）

デスクトップアプリのサイドバーで **Routines** をクリックし、**New routine** → **Cloud** を選ぶと作成フォームが開きます（**Local** を選ぶと後述のデスクトップスケジュールタスクになります）。Web の [claude.ai/code/routines](https://claude.ai/code/routines) で **New routine** を押した場合も、同じフォームが開きます。

フォームは上から順に埋めていきます。

```text
1. 名前とプロンプトを書く（実行するモデルもここで選ぶ）
       ↓
2. 対象リポジトリを選ぶ（複数可）
       ↓
3. 実行環境を選ぶ（ネットワーク・環境変数・セットアップスクリプト）
       ↓
4. 「Select a trigger」できっかけを選ぶ（スケジュール / GitHub / API）
       ↓
5. 「Connectors」で不要な外部サービス連携を外す
       ↓
6. 「Create」を押して保存
```

各項目のポイントは次のとおりです。

| 項目 | 書くこと・注意点 |
| --- | --- |
| 名前 | 一覧で見分けがつく名前を付ける |
| プロンプト | **最重要**。自律実行されるため、会話で補足できない。「何をするか」と「何をもって完了とするか」をこの文章だけで判断できるように書く |
| モデル | プロンプト入力欄にセレクタがある。毎回このモデルで実行される |
| リポジトリ | 実行のたびに既定ブランチから取得し直される。Claude は `claude/` で始まるブランチに変更を書き込む |
| 実行環境 | 既定の **Default** 環境で足りることが多い。自社サービスに直接アクセスしたい場合のみ変更が必要（後述） |
| きっかけ | 1 つの Routine に複数付けられる。「毎晩動きつつ、新しい PR でも動く」といった構成が可能 |
| Connectors | **連携済みの外部サービスが既定で全部入る**。不要なものは必ず外す（後述） |

#### 保存したあとに手動で実行する

作成した Routine は、一覧からクリックすると詳細ページが開きます。ここが運用の中心になります。

| ボタン・操作 | できること |
| --- | --- |
| **Run now** | 次のスケジュールを待たずに **今すぐ 1 回実行する**。実行時だけの補足テキストを添えることもできる |
| **Repeats** セクションのトグル | スケジュールを一時停止 / 再開する。設定は保持されたまま止まる |
| 鉛筆アイコン（**Edit routine**） | 名前・プロンプト・リポジトリ・環境・連携・きっかけを変更する |
| 削除アイコン | Routine を削除する。過去の実行セッションは残る |
| 実行履歴の各行 | クリックすると、その回のセッションが開く。Claude が何をしたかを最初から追える |

> [!TIP]
> **作ったらまず `Run now` を押してください。** 自律実行は「動かしてみないと分からない」部分が多く、プロンプトの曖昧さ・権限不足・ネットワーク制限はすべて実際の実行ログにしか現れません。スケジュールを待つ前に 1 回試すのが確実です。

実行のたびに新しいセッションが作られ、通常のセッションと同じ場所に並びます。そこから変更内容をレビューしたり、プルリクエストを作ったり、会話の続きを手動で書いたりできます。

### CLI から作る

エディタのターミナルで作業している最中なら、`/schedule` コマンド（別名 `/routines`）で会話しながら作るほうが速いこともあります。

```text
/schedule 毎朝 9 時に PR レビューを実行して
```

Claude がスケジュール・対象リポジトリ・プロンプトについて質問しながら、Routine を保存してくれます。

> [!NOTE]
> **指示は日本語で構いません。** `/schedule` に渡す文章も、Routine 本体のプロンプトも、Claude が自然言語として解釈するものです。英語で書く必要はありません。cron 式やリポジトリ名のような機械が解釈する値だけが、決まった書式を要求します。

作成後の管理も CLI から行えます。

| コマンド | 用途 |
| --- | --- |
| `/schedule list` | 登録済みの Routine を一覧する |
| `/schedule update` | 設定を変更する（cron 式の直接指定もここ） |
| `/schedule run` | 今すぐ 1 回実行する |

実行結果について質問することもできます。Claude が実行履歴とログを読んで、ツールのエラーや権限拒否まで含めて説明してくれます。

```text
/schedule 今朝の夜間レビューが何もしなかったのはなぜ？
```

ただし CLI には制約があります。**API トリガーの追加とトークンの発行・失効は Web の画面からしか行えません。** GitHub イベントトリガーは CLI からも追加できます（Claude Code v2.1.225 以降）。

### 3 種類のトリガー（きっかけ）

Routines の最大の特徴は、時刻以外のきっかけで動かせることです。

| きっかけ | 起動条件 | 主な用途 |
| --- | --- | --- |
| スケジュール | 毎時 / 毎日 / 平日 / 毎週、または将来の特定時刻に 1 回 | 定期レビュー、バックログ整理、ドキュメントの陳腐化チェック |
| API | 専用の URL に HTTP リクエストが届いたとき | 監視ツールのアラート連携、デプロイ後の検証 |
| GitHub | リポジトリで PR やリリースの動きがあったとき | PR の自動レビュー、リリース時の連動処理 |

1 つの Routine に複数のきっかけを付けられるため、「毎晩定期実行しつつ、新しい PR が来たときにも走る」といった構成が可能です。

#### きっかけを追加する共通手順

きっかけは作成フォームでも指定できますが、あとから追加・変更する場合は、**3 種類とも次の手順までは共通** です。

```text
1. claude.ai/code/routines を開き、対象の Routine をクリック
       ↓
2. 鉛筆アイコンを押して「Edit routine」を開く
       ↓
3. 「Instructions」欄の下にある「Select a trigger」までスクロール
       ↓
4. 「Add another trigger」を押し、追加する種類を選ぶ
```

種類を選んだあとの設定内容だけが異なります。以降の各節では、その固有の部分を説明します。

#### スケジュールトリガー

種類として **Schedule** を選ぶと、毎時・毎日・平日・毎週のプリセットから選択できます。時刻は自分のタイムゾーンで入力すれば自動で変換されるため、クラウドの所在地に関わらず指定した時刻に実行されます。

「2 時間おき」「毎月 1 日」のようなプリセットにない間隔は、フォームで近いプリセットを選んだうえで、CLI の `/schedule update` から **cron 式**（`分 時 日 月 曜日` の 5 項目で繰り返しを表す記法）を直接指定します。**最短間隔は 1 時間** で、それより短い式は拒否されます。

> [!NOTE]
> 実行はスケジュール時刻から数分ずれることがあります。同時刻にアクセスが集中しないよう、意図的に少しずらして起動する仕組みです。ずれ幅は Routine ごとに一定で、毎回同じだけずれます。

単発実行も設定できます。「ロールアウト完了後にクリーンアップ PR を出す」「2 週間後にフィーチャーフラグを削除する」といった用途に向いており、実行後は自動的に無効化されて一覧に **Ran** と表示されます。**単発実行は 1 日あたりの実行回数上限にカウントされません**。

```text
/schedule 2 週間後に、フィーチャーフラグを削除するクリーンアップ PR を作って
```

#### API トリガー

**何のための機能か。** 「監視ツールがエラーを検知したら」「デプロイが完了したら」のように、**Claude 以外のシステムを起点に Claude を動かしたい** ときに使います。時刻では表せないタイミングで、外部のツールから声をかけてもらう窓口を作る、というイメージです。

仕組みとしては、その Routine 専用の受付 URL（エンドポイント）と、そこを呼ぶための合言葉（トークン）が発行されます。監視システム・デプロイパイプライン・社内ツールなど、HTTP リクエストを送れる場所ならどこからでも起動できます。

##### 設定手順

API トリガーは、**既存の Routine に対して Web の画面から追加します**（CLI では追加できません）。共通手順で **API** を選ぶとモーダルが開くので、そこから続けます。

```text
1. モーダルに表示された URL をコピーする
       ↓
2. 「Generate token」を押し、表示されたトークンをその場でコピーする
       ↓
3. 呼び出す側のツールに、この URL とトークンを登録する
```

> [!WARNING]
> **トークンは生成時に一度しか表示されません。** モーダルを閉じると二度と取得できないため、その場で監視ツールのシークレット保管領域などにコピーしてください。紛失した場合は、同じモーダルの **Regenerate**（再発行）で作り直します。**Revoke** を押せば無効化できます。トークンはその Routine を起動する用途にのみ有効です。

##### 呼び出す側の設定

呼び出す側では、コピーした URL に対して、トークンを添えた HTTP リクエストを送ります。設定するのは「URL」「ヘッダー」「ボディ」の 3 つだけです。

ヘッダーには次の 4 つを指定します。

| ヘッダー | 値 | 役割 |
| --- | --- | --- |
| `Authorization` | `Bearer <発行したトークン>` | 認証（これがないと `401` エラー） |
| `anthropic-beta` | `experimental-cc-routine-2026-04-01` | 研究プレビュー版の機能を使う宣言 |
| `anthropic-version` | `2023-06-01` | API のバージョン指定 |
| `Content-Type` | `application/json` | ボディの形式 |

手元で動作確認したい場合は次のようなコマンドで試せます。

```bash
# 監視ツールのアラートを Routine に渡して調査させる（URL とトークンは設定手順でコピーしたもの）
curl -X POST https://api.anthropic.com/v1/claude_code/routines/trig_XXXXXXXX/fire \
  -H "Authorization: Bearer sk-ant-oat01-xxxxx" \
  -H "anthropic-beta: experimental-cc-routine-2026-04-01" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"text": "Sentry のアラート SEN-4521 が本番で発生。スタックトレースは添付のとおり。"}'
```

ボディの `text` は任意項目で、**その回だけの補足情報**（アラートの本文やエラーログなど）を渡すために使います。詳細ページの **Run now** に添えるテキストも、これと同じ扱いで届きます。

成功するとセッション ID と URL が返り、ブラウザで実行の様子をリアルタイムに追えます。

```text
{
  "type": "routine_fire",
  "claude_code_session_id": "session_01HJKLMNOPQRSTUVWXYZ",
  "claude_code_session_url": "https://claude.ai/code/session_01HJKLMNOPQRSTUVWXYZ"
}
```

> [!IMPORTANT]
> **`text` に書いた内容は、そのままでは指示として扱われません。** Claude には「信頼できない外部データ」というラベル付きで渡されるため、Routine 側のプロンプトが「`routine-fire-payload` ブロックに記載されたアラートを調査してください」のように**明示的に参照しない限り、無視されます**。これは、トークンが漏れた場合に第三者から任意の命令を送り込まれることを防ぐための設計です。API トリガーを使う Routine では、プロンプト側にこの参照を必ず書いてください。

##### 呼び出し元の具体例

「HTTP リクエストを送れる場所」と言われてもイメージしづらいので、代表的な呼び出し元を挙げます。

| 呼び出し元 | 典型的な用途 | 設定方法 |
| --- | --- | --- |
| 監視・アラート SaaS（Datadog・Sentry・PagerDuty・Grafana など） | エラー急増や閾値超過をきっかけに、原因調査と修正 PR の起票まで走らせる | 通知先の Webhook として URL とヘッダーを登録する |
| GitHub Actions などの CI/CD | デプロイ完了後の検証、リリース後の後始末 | ワークフローのステップで `curl` を実行する |
| サーバの cron | プリセットにない細かい間隔で回したい | シェルスクリプトを cron から呼び出す |
| ノーコード自動化ツール（Zapier・n8n・Make など） | 他の SaaS の出来事を中継して Claude に渡す | 「HTTP リクエスト」系のアクションで POST する |
| 社内の業務システム | 申請の受理や在庫の異常など、業務イベントを起点に動かす | アプリのコードから HTTP クライアントで POST する |

> [!IMPORTANT]
> **必要なのは「カスタムヘッダーを設定できる」呼び出し元です。** 前述のとおりヘッダーを 4 つ指定する必要があるため、**送信先の URL しか指定できない簡易的な Webhook 機能からは直接呼び出せません**。使いたいツールの Webhook 設定画面に、ヘッダーを追加する入力欄があるかを先に確認してください。無い場合は、CI のジョブや小さなスクリプトを間に挟んで中継します。

**例 1: GitHub Actions からデプロイ後の検証を依頼する**

トークンはリポジトリのシークレット（例: `CLAUDE_ROUTINE_TOKEN`）に登録し、ワークフローからは環境変数として参照します。

```yaml
# .github/workflows/deploy.yml の一部
- name: デプロイ後の検証を Routine に依頼
  env:
    ROUTINE_TOKEN: ${{ secrets.CLAUDE_ROUTINE_TOKEN }}
  run: |
    curl -sS --fail-with-body -X POST https://api.anthropic.com/v1/claude_code/routines/trig_XXXXXXXX/fire \
      -H "Authorization: Bearer $ROUTINE_TOKEN" \
      -H "anthropic-beta: experimental-cc-routine-2026-04-01" \
      -H "anthropic-version: 2023-06-01" \
      -H "Content-Type: application/json" \
      -d "{\"text\": \"コミット ${GITHUB_SHA} を本番へデプロイしました。スモークテストとエラーログの確認をお願いします。\"}"
```

**例 2: サーバの cron から定期的に起動する**

cron の設定行は複数行に分けられないため、`curl` はスクリプトに切り出しておきます。

```bash
#!/usr/bin/env bash
# ~/bin/fire-routine.sh
curl -sS --fail-with-body -X POST https://api.anthropic.com/v1/claude_code/routines/trig_XXXXXXXX/fire \
  -H "Authorization: Bearer $(cat ~/.secrets/claude-routine-token)" \
  -H "anthropic-beta: experimental-cc-routine-2026-04-01" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"text": "定期チェックの時刻になりました。"}'
```

```text
# crontab -e に登録（15 分おきに実行）
*/15 * * * * ~/bin/fire-routine.sh
```

> [!TIP]
> この方法は、**Cloud Routines のスケジュールの最短間隔（1 時間）を回避する手段** にもなります。ただし cron を動かすサーバを常時稼働させる必要があり、1 日あたりの実行回数上限も通常どおり消費します。単に頻度が欲しいだけであれば、まず `/loop` やデスクトップスケジュールタスクで足りないかを検討してください。

> [!NOTE]
> この API は `experimental-cc-routine-2026-04-01` というベータ指定の下で提供されています。研究プレビュー中はリクエスト・レスポンスの形や上限が変わる可能性があります。

#### GitHub イベントトリガー

**どうやって GitHub と繋がっているのか。** 鍵になるのは **Claude GitHub App** です。これを対象リポジトリにインストールすると、GitHub がそのリポジトリの出来事（PR が作られた、リリースが公開された、など）を Anthropic 側へ自動通知するようになります。Routine 側は「どのリポジトリの、どのイベントに反応するか」を登録しておき、通知が条件に一致したときにセッションを起動します。

```text
GitHub で PR が作成される
       ↓
Claude GitHub App が入っているので、GitHub が Anthropic に通知を送る
       ↓
Routine に登録した「リポジトリ・イベント・フィルタ」と照合
       ↓
条件に一致 → クラウドでセッションが 1 つ起動し、保存済みプロンプトを実行
       ↓
Claude が PR にコメントを付ける / 修正をプッシュする など
```

つまり、**GitHub 側で Actions のワークフローを書いたり、Webhook を手で設定したりする必要はありません**。GitHub App を入れることが、実質的な「連携設定」です。

> [!IMPORTANT]
> CLI の `/web-setup` はリポジトリを取得するためのアクセス権を与えるだけで、**GitHub App のインストールとイベント通知の有効化は行いません**。両者は別物なので、`/web-setup` 済みでもイベントトリガーは動きません。

イベントごとに独立したセッションが作られます。PR が 2 回更新されれば 2 つのセッションが立ち上がる、という点は把握しておいてください。

##### 設定手順

共通手順で **GitHub event** を選んだあと、次の設定を行います。

```text
1. （App が未インストールなら）案内に従って Claude GitHub App を入れる
       ↓
2. 対象リポジトリと、反応するイベントを選ぶ
       ↓
3. 必要ならフィルタを追加して保存する
```

CLI から設定する場合は、先に [GitHub App のページ](https://github.com/apps/claude)からインストールを済ませたうえで、日本語で依頼できます（Claude Code v2.1.225 以降）。

```text
/schedule 夜間レビューの Routine に、acme/webapp で PR が作成されたら動く GitHub トリガーを追加して
```

##### 反応できるイベント

| イベント | 発火タイミング |
| --- | --- |
| Pull request | PR が作成 / クローズ / アサイン / ラベル付け / 更新（新しいコミットのプッシュ）されたとき |
| Release | リリースが作成 / 公開 / 編集 / 削除されたとき |

それぞれ「作成されたときだけ」のように特定の動作に絞ることも、そのカテゴリのすべての動作に反応させることもできます。

##### フィルタで対象を絞る

すべての PR で起動すると実行回数を無駄に消費するため、通常はフィルタで絞り込みます。指定した条件は **すべて満たされた場合のみ** 起動します。

| フィルタ項目 | 対象 |
| --- | --- |
| Author | PR 作成者の GitHub ユーザー名 |
| Title / Body | PR のタイトル / 本文 |
| Base branch / Head branch | マージ先 / マージ元のブランチ |
| Labels | 付与されたラベル |
| Is draft / Is merged | ドラフトかどうか / マージ済みかどうか |

各項目には「equals（完全一致）」「contains（含む）」「starts with（で始まる）」「is one of（いずれかに一致）」「is not one of（いずれにも一致しない）」「matches regex（正規表現に一致）」の演算子を組み合わせます。

実際の設定例を挙げます。

| やりたいこと | フィルタの指定 |
| --- | --- |
| 認証まわりの PR だけ重点レビューする | Base branch が `main` かつ Head branch が `auth-provider` を含む |
| 書きかけの PR は無視する | Is draft が `false` |
| ラベルが付いたときだけバックポートする | Labels に `needs-backport` を含む |

> [!CAUTION]
> `matches regex` は **項目の値全体** に対する一致判定です。タイトルに `hotfix` を含むものを拾いたい場合は `.*hotfix.*` と書く必要があります。`hotfix` だけを指定すると、タイトルがちょうど `hotfix` の PR にしかマッチしません。単に「含む」で足りるなら `contains` を使うほうが安全です。

> [!NOTE]
> 研究プレビュー中は、GitHub イベントによる起動に **Routine ごと・アカウントごとの 1 時間あたりの上限** があります。上限を超えたイベントは、次の時間枠まで破棄されます。現在の上限は [claude.ai/code/routines](https://claude.ai/code/routines) で確認できます。

### 実行環境とネットワーク

Routine はクラウド上の実行環境で動き、この環境が**外部との通信範囲・環境変数・事前セットアップ**を決めます。

既定の **Default** 環境は **Trusted** という設定で、パッケージ配布サイトやクラウド事業者の API など、あらかじめ許可されたドメインのみ通信できます。許可外のホストへのリクエストは `403` エラー（`x-deny-reason: host_not_allowed`）で失敗します。自社サービスに直接アクセスする必要がある場合は、環境設定でネットワークアクセスを **Custom** に変更してドメインを追加します。

```text
1. Routine の詳細ページで鉛筆アイコン →「Edit routine」
       ↓
2. 「Instructions」欄の下の、環境名（例:「Default」）が付いた雲アイコンを選ぶ
       ↓
3. 一覧で環境にカーソルを合わせ、右に出る設定アイコンをクリック
       ↓
4. 「Network access」を「Custom」にし、「Allowed domains」にドメインを入力
   （既定の許可リストも残したい場合は下のチェックボックスをオンにする）
       ↓
5. 「Save changes」で保存。次回の実行から適用される
```

> [!NOTE]
> Slack や Linear などのコネクタ経由の通信は Anthropic のサーバを経由するため、**許可リストへの追加は不要** です。コネクタを使う Routine のためにドメインを開ける必要はありません。

リポジトリは実行のたびに既定ブランチから取得し直されます。Claude は変更を `claude/` で始まるブランチにプッシュします。プロンプトで別のブランチを指定した場合、保護ブランチ・他人の PR が出ているブランチ・他人のコミットを含むブランチへのプッシュは拒否されます。

### 人が見ていない場所で動くことの注意

Routines は **確認プロンプトのない完全自律セッション** として動作します。権限モードの選択肢はなく、実行中に「これを実行してよいですか」と聞かれることもありません。

> [!CAUTION]
> Routine に含めた外部サービス連携について、Claude は **書き込みを含むすべての操作を許可なく実行できます**。作成フォームでは連携済みのサービスが既定ですべて含まれるため、**その Routine に不要な連携は必ず外してください**。同様に、環境変数は同じ環境を使う全員から見えるため、認証情報を置く際は注意が必要です。

もう 1 つの落とし穴が実行結果の見方です。

> [!IMPORTANT]
> 実行一覧のステータスが緑になっていても、それは **セッションがシステム的なエラーなく起動・終了した** ことを示すだけで、**依頼したタスクが成功したことは意味しません**。通信のブロック、連携ツールの不足、作業そのものの失敗はいずれもステータスには現れません。実際に何が起きたかは、実行履歴を開いて会話ログを読む必要があります。

### 実行回数の上限

Routines は通常のセッションと同じようにサブスクリプションの使用量を消費します。それに加えて、**アカウントごとに 1 日あたりの起動回数の上限** があります。上限に達すると、使用クレジットを有効にしている場合は従量課金で継続でき、そうでなければ枠がリセットされるまで拒否されます。

Team / Enterprise では、オーナーが管理画面のトグルで組織全体の Routines を無効化できます。無効化すると既存の Routine も停止します。

## デスクトップスケジュールタスク

手元のフォルダにあるファイルや、自分のパソコンにしか入っていないツールを使う必要がある場合は、こちらを使います。デスクトップアプリのサイドバーで **Routines** → **New routine** → **Local** を選ぶと作成できます（**Cloud** を選ぶと前述の Cloud Routines になります）。

### 設定項目

| 項目 | 内容 |
| --- | --- |
| Name | タスクの名前。小文字ハイフン区切りに変換され、そのままディスク上のフォルダ名になる |
| Description | 一覧に表示される短い説明 |
| Instructions | 実行内容。通常のプロンプトと同じ書き方でよい。権限モードとモデルの選択、作業フォルダの指定もここで行う |
| Schedule | 実行頻度（Manual / Hourly / Daily / Weekdays / Weekly） |

作業フォルダの指定は必須です。**Manual** を選ぶとスケジュール実行はされず、手動で **Run now** を押したときだけ動きます（よく使うプロンプトを保存しておく用途に便利です）。プリセットにない間隔は、任意のセッションで「テストを 6 時間おきに実行するタスクを作って」のように日本語で頼めば設定できます。

> [!TIP]
> 既定ではタスクは **作業フォルダの現在の状態**（コミットしていない変更を含む）に対して実行されます。作成時にワークツリーのトグルを有効にすると、実行ごとに独立した作業コピーが割り当てられ、進行中の自分の作業と干渉しなくなります。

### 実行条件と取りこぼし

タスクが動くのは **デスクトップアプリが起動していて、かつパソコンが起きている間だけ** です。スリープ中にスケジュール時刻を過ぎると、その回は実行されません。設定の「Keep computer awake」で放置によるスリープは防げますが、ラップトップの蓋を閉じればスリープします。

取りこぼしには救済措置があります。アプリ起動時やスリープ復帰時に、過去 7 日以内の未実行がないか確認され、**直近 1 回分だけ** が遅れて実行されます。6 日間実行できなかった日次タスクも、復帰時に走るのは 1 回だけです。

> [!WARNING]
> この遅れての実行があるため、**朝 9 時に設定したタスクが夜 11 時に動く** ことがあります。時刻が意味を持つプロンプトには、あらかじめ歯止めを書き込んでおいてください。たとえば「本日のコミットのみをレビューしてください。17 時を過ぎている場合はレビューをスキップし、未処理分の要約だけを報告してください」のように書きます。

### 権限

タスクごとに権限モードを設定でき、`~/.claude/settings.json` の許可ルールも適用されます。手動承認モードで権限のないツールを使おうとすると、**承認されるまで実行が止まります**。セッションはサイドバーに残るので後から答えることもできますが、無人実行を前提にするなら避けたい挙動です。

停止を防ぐには、タスク作成後に一度 **Run now** を実行し、出てくる確認ダイアログで「always allow」を選んでおきます。以降の実行では同じツールが自動承認されます。承認内容はタスクの詳細ページから確認・取り消しできます。

### タスクの実体

プロンプトはディスク上にファイルとして保存されており、直接編集できます。

```bash
# タスクのプロンプトを編集する
$EDITOR ~/.claude/scheduled-tasks/<task-name>/SKILL.md
```

このファイルは `name` と `description` を先頭のメタ情報に持ち、本文がプロンプトになります。変更は次回実行から反映されます。スケジュール・フォルダ・モデル・有効状態はこのファイルには含まれないため、編集フォームか Claude への依頼で変更します。

## `/loop`（セッション内スケジュール）

`/loop` は、**開いているセッションの中でプロンプトを繰り返す** 組み込みスキルです。前の 2 つと違って設定を保存する仕組みではなく、**その場限りの見張り役** を立てるためのものだと考えてください。

### `/loop` が役に立つ場面

「定期実行なら Cloud Routines でよいのでは」と感じるかもしれませんが、`/loop` には他の 2 つにない性質があります。**今この会話が持っている文脈をそのまま引き継ぐ** という点です。

Cloud Routines のプロンプトは、会話の履歴を持たない状態から始まるため自己完結している必要があります。一方 `/loop` は、直前まで作業していた内容・開いていたファイル・実行したコマンドの結果をすべて把握したうえで繰り返します。だから **「さっきの続きを見ていて」** という曖昧な指示が成立します。

実際に効く場面は次のようなものです。

| 場面 | 使い方 | なぜ `/loop` が向くか |
| --- | --- | --- |
| 自分が出した PR を、マージできる状態まで持っていく | 引数なしの `/loop`（後述の組み込みプロンプト） | CI の失敗もレビューコメントもコンフリクトも、1 つのループが順に片付ける |
| 15 分かかるビルドやデプロイの完了を待つ | `/loop 5m ビルドが終わったか確認して` | 終わり次第すぐ次の作業に入れる。人が待つ必要がない |
| 長時間かかる移行作業を、対象がなくなるまで繰り返す | `/loop 残っている呼び出し箇所を 1 ファイル分だけ移行して` | 1 回のセッションで文脈が溢れる規模の作業を、少しずつ確実に進められる |
| 依頼したレビューが返ってくるまで待つ | `/loop レビューコメントが付いていたら対応して` | 動きがない間は待ち時間を長く取るので、無駄な実行が減る |
| あとで自分に思い出させる | `45 分後に、結合テストが通ったか確認して` | 単発のリマインダーとして使える |

> [!TIP]
> **セッションをバックグラウンドに送れば、ターミナルを閉じてもループは動き続けます。** 「開いておかないといけない」という制約は、思っているより緩いものです。

逆に **向かない** のは、毎日決まった時刻に回したい定型業務です。7 日で自動的に消える仕様（後述）があるため、恒久的な自動化は Cloud Routines かデスクトップスケジュールタスクに任せてください。

### 3 つの使い方

渡す引数によって挙動が変わります。

| 渡すもの | 例 | 挙動 |
| --- | --- | --- |
| 間隔とプロンプト | `/loop 5m デプロイの状況を確認して` | 固定間隔で実行 |
| プロンプトのみ | `/loop デプロイの状況を確認して` | Claude が毎回、次までの待ち時間を判断して実行 |
| 間隔のみ / 何もなし | `/loop` | 組み込みのメンテナンスプロンプト（または `loop.md`）を実行 |

**固定間隔** は `s`（秒）/ `m`（分）/ `h`（時）/ `d`（日）の単位で指定します。秒は分に切り上げられ、`7m` や `90m` のようにきりの悪い値は近い値に丸められます（丸めた結果は Claude が教えてくれます）。

**間隔を省略** すると、Claude が各回の結果を見て 1 分〜1 時間の範囲で次の待ち時間を決めます。ビルドが終わりかけていれば短く、動きがなければ長く待つ、という調整が入ります。選んだ間隔とその理由は毎回表示されます。

```text
/loop CI が通ったか確認し、レビューコメントが来ていれば対応して
```

スキルを渡すこともできます（`/loop 20m /review-pr 1234`）。ただし `/model` のような組み込みコマンドや、Claude 自身が呼び出せない設定になっているスキルは実行されず、単なる文字列として渡ります。

### 引数なしの `/loop` は何をするのか

`/loop` を単体で打つと、Claude Code に組み込まれた **メンテナンスプロンプト** が動きます。中身は毎回、次の順に確認していく指示です。

```text
1. 会話の中でやりかけになっている作業を片付ける
       ↓
2. 現在のブランチの PR を世話する
   （レビューコメントへの対応 / 失敗した CI の修正 / コンフリクトの解消）
       ↓
3. どれも該当しなければ、バグ探しやコードの整理を行う
```

これが `/loop` の実用性の中心です。**「PR を出したあと、マージできる状態になるまで面倒を見る」** という、地味に手間のかかる工程を丸ごと任せられます。

暴走しないための歯止めも入っています。この範囲を超えて新しい作業を勝手に始めることはなく、プッシュや削除のような取り返しのつかない操作は、**会話の中ですでに承認済みの作業を続ける場合にのみ** 実行されます。

### `loop.md` で既定のプロンプトを差し替える

引数なしの `/loop` が使うプロンプトは、`loop.md` というファイルを置くことで自分用の内容に差し替えられます。

| パス | スコープ |
| --- | --- |
| `.claude/loop.md` | プロジェクト単位（両方ある場合はこちらが優先） |
| `~/.claude/loop.md` | ユーザー単位 |

中身は構造の決まっていない普通の Markdown です。`/loop` にそのまま打ち込む文章を書く感覚で構いません。

```markdown
`release/next` の PR を確認してください。CI が失敗していれば失敗したジョブの
ログを取得し、原因を診断して最小限の修正をプッシュしてください。新しい
レビューコメントが来ていれば、それぞれに対応してスレッドを解決してください。
すべて問題なく静かであれば、その旨を 1 行で報告してください。
```

編集は次の周回から反映されるため、ループを走らせたまま指示を調整できます。25,000 バイトを超える内容は切り詰められるので簡潔に保ってください。

> [!TIP]
> 「一定時間ごとに問い合わせる」こと自体が無駄な場合もあります。ログの出力を待つだけなら、Claude は `/loop` の代わりに **Monitor ツール** を使うことがあります。バックグラウンドでコマンドを走らせて出力行をそのまま流す仕組みで、繰り返し問い合わせる必要がないぶん、費用と反応速度の両面で有利です。

### 停止と自動失効

待機中に `Esc` を押すとループが止まります。間隔を Claude に任せているモードでは、タスクが完了したと判断すれば Claude 自身がループを終了することもあります。周回の最後に次回の予約も終了もされなかった場合は、約 20 分後に 1 回だけ予備の実行が入り、そこでも予約がなければ終了します。

> [!IMPORTANT]
> 繰り返しタスクは **作成から 7 日で自動的に失効** します。最後に 1 回だけ実行してから自分自身を削除する仕様で、忘れられたループが動き続けるのを防ぐためのものです。7 日を超えて回したい場合は、失効前に作り直すか、Cloud Routines かデスクトップスケジュールタスクを使ってください。

### 時刻まわりのクセ

`/loop` の裏側では cron ベースのスケジューラが動いています。実務で引っかかりやすい仕様を挙げます。

- **タイムゾーン**: すべて自分のタイムゾーンで解釈されます。`0 9 * * *` は UTC の 9 時ではなく、Claude Code を動かしている場所の 9 時です。
- **実行のタイミング**: スケジューラは毎秒チェックしますが、プロンプトが実行されるのは **応答と応答の間** です。Claude が回答している最中であれば、それが終わるまで待ちます。
- **時刻のずれ**: アクセスが同時刻に集中しないよう、実行時刻には決まった量のずれが加わります。**固定間隔の繰り返しタスク**は最大 30 分（1 時間未満の間隔なら間隔の半分まで）遅れて実行されます。**単発タスク**は `:00` または `:30` を指定した場合に限り、最大 90 秒 **早く** 実行されます。ずれ幅はタスクごとに決まっているため、同じタスクなら毎回同じです。**間隔を Claude に任せるモードには、このずれは適用されません**（毎回その場で待ち時間を決めるため）。
- **取りこぼしの補填なし**: 長い処理の最中に時刻を過ぎた場合、手が空いた時点で 1 回だけ実行されます。逃した回数分は実行されません。
- **セッションの寿命**: 新しい会話を始めるとタスクは消えます。`claude --resume` / `--continue` で再開すると、7 日以内に作った繰り返しタスクと、まだ時刻が来ていない単発タスクが復元されます。

> [!IMPORTANT]
> 時刻のずれを避けられるのは **単発タスクだけ** です。`0 9 * * *` ではなく `3 9 * * *` のように `:00` / `:30` 以外の分を選べば、単発タスクの 90 秒の前倒しは適用されなくなります。一方、**固定間隔の繰り返しタスクにおける最大 30 分の遅れは、分の選び方では回避できません**。分単位の正確さが必要な定期実行には、`/loop` ではなく OS の cron など別の手段を検討してください。

一回限りのリマインダーは日本語で頼めます。

```text
45 分後に、結合テストが通ったか確認して
```

タスクの一覧や取り消しも同様です。内部的には `CronCreate` / `CronList` / `CronDelete` の 3 つのツールが使われ、1 セッションで最大 50 件まで登録できます。

```text
今どんな定期タスクが登録されている？
```

> [!NOTE]
> スケジューラを完全に止めたい場合は、環境変数 `CLAUDE_CODE_DISABLE_CRON=1` を設定します。cron ツールと `/loop` が使えなくなり、登録済みのタスクも実行されなくなります。

## 使い分けの実例

| やりたいこと | 適した方式 | 理由 |
| --- | --- | --- |
| 平日朝に前日マージ分のリリースノート案を作る | Cloud Routines | パソコンの状態に依存せず確実に回したい |
| 新しい PR にチーム独自のレビュー観点を適用する | Cloud Routines（GitHub トリガー） | 出来事をきっかけに動かせるのはクラウドのみ |
| 監視アラートを受けて調査と修正 PR を起票する | Cloud Routines（API トリガー） | 外部システムから起動する必要がある |
| ドキュメントが実装に追いついているか毎週点検する | Cloud Routines | 頻度が低く、手元の環境も不要 |
| 手元の作業フォルダを毎晩整理する | デスクトップスケジュールタスク | ローカルファイルにアクセスする必要がある |
| ローカルの開発 DB に対してテストを定期実行する | デスクトップスケジュールタスク | 手元のツールと環境が必要 |
| 今出した PR を、CI 修正まで含めてマージ可能にする | `/loop`（引数なし） | 直前までの作業文脈をそのまま引き継げる |
| 走らせたビルドの完了を待って結果を知りたい | `/loop 5m ...` | 一時的な見張りで十分 |
| 大量の置換作業を、対象がなくなるまで少しずつ進める | `/loop`（間隔省略） | 1 セッションに収まらない量を分割して進められる |

## 注意点と落とし穴

無人で動く自動化は、便利さと引き換えに「気付かないうちに何かが起きる」リスクを持ちます。

> [!CAUTION]
> **取り返しのつかない操作を自動化の対象にしない。** 送金・メッセージ送信・本番環境への反映・データ削除といった操作は、確認を挟めない Cloud Routines には向きません。まずは調査・要約・下書き作成といった読み取り中心のタスクから始め、実行履歴を定期的に見るようにしてください。

> [!WARNING]
> **プロンプトは自己完結させる。** Routine は自律実行されるため、会話の流れで補足することができません。「何をするか」と「何をもって完了とするか」を、そのプロンプトだけで判断できるように明記する必要があります。

> [!WARNING]
> **外部サービス連携と環境変数の範囲を絞る。** Routine に含めた連携先の操作は、書き込みを含めて許可なく実行されます。不要なものは外してください。

| 症状・制限 | 対処 |
| --- | --- |
| `/loop` のタスクが 7 日で消えた | 仕様。恒久的に回すなら Cloud Routines かデスクトップスケジュールタスクへ移行する |
| デスクトップタスクが動いていない | アプリが起動しているか、パソコンがスリープしていないかを確認する。実行履歴でスキップ理由を確認できる |
| デスクトップタスクが権限待ちで止まる | 一度 **Run now** して「always allow」を選び、必要なツールを事前に承認しておく |
| 実行ステータスは緑なのに成果物がない | ステータスは起動と終了しか見ていない。実行履歴を開いて会話ログを確認する |
| GitHub にイベントを起こしても Routine が動かない | Claude GitHub App が対象リポジトリにインストールされているか確認する（`/web-setup` だけでは有効にならない）。フィルタ条件が厳しすぎないかも見直す |
| API トリガーに渡した `text` が無視される | 仕様。Routine のプロンプト側で `routine-fire-payload` ブロックを参照するよう明記する |
| Routine から自社 API に到達できない | クラウド環境のネットワークアクセスを Custom にしてドメインを追加する |
| `/schedule` が「Unknown command」になる | claude.ai アカウントでのログインが必要。API キー認証やクラウド事業者経由のログインでは使えない |

## まとめ

- Claude Code のスケジュール実行には **Cloud Routines / デスクトップスケジュールタスク / `/loop`** の 3 方式がある
- 選択の基準は **パソコンの状態に左右されず回したいか**・**手元のファイルが必要か**・**Claude Code を開いたままでよいか** の 3 点
- Cloud Routines は **デスクトップアプリまたは Web のフォームから作成** し、詳細ページの **Run now** でいつでも手動実行できる
- Cloud Routines だけが **時刻以外のきっかけ**（API・GitHub イベント）を持ち、複数のきっかけを 1 つの Routine に併用できる
- **GitHub 連携の実体は Claude GitHub App のインストール**。App が通知経路を作り、Routine 側のフィルタが一致したときにセッションが起動する
- Cloud Routines は **確認プロンプトのない完全自律実行**。連携先と環境変数の範囲を絞り、取り返しのつかない操作は任せない
- デスクトップタスクは **アプリ起動中かつ非スリープ時のみ** 動作し、取りこぼしは直近 1 回だけ遅れて実行される
- `/loop` の価値は **直前までの作業文脈を引き継げること**。引数なしの `/loop` は「PR をマージできる状態まで面倒を見る」用途で特に有効
